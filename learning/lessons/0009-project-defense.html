五分钟陈述模板

  1. 问题（30 秒）：系统面向 Ethereum/Base 的地址资金分析，目标是在可控成本下展示可回查的资金事实、图关系和协议解释。
  2. 证据（60 秒）：普通 ETH 来自顶层 transaction，ERC-20 来自成功 receipt 的 Transfer log，内部 ETH 来自 trace/indexer；不同来源不混同。
  3. 架构（90 秒）：Etherscan/indexer 供地址历史，RPC 供 transaction、receipt、logs 与 eth_call；syncer 异步分页、检查点、批量幂等写 Mongo；查询层只读本地事实，tracer 有界 BFS。
  4. 协议与跨链（60 秒）：Uniswap 用 receipt 和 Pool Factory 验证实际 Swap；桥用 Ethereum/Base 双链官方消息建状态机。
  5. 边界与演进（60 秒）：图不是逐币归因；存在上游、窗口和裁剪限制。生产化会做多 RPC、reorg 回滚、任务队列、可观测性和更完整自建索引。

系统设计追问速答

问题可靠回答
为什么异步同步？外部历史查询有分页、限流和不确定延迟；把它从用户查询路径分离，任务可恢复且结果可标记 partial。
如何避免重复数据？用 chain、tx、source 和交易内证据位置构成稳定身份，Mongo upsert；不只用 txHash。
高频地址如何控制？限制 depth、Top-N、时间窗和终点；稳定排序、游标分页，并显式声明裁剪。
如何处理 reorg？使用 safe/finalized 策略或确认数，保留可重扫窗口和幂等写入；不能把 latest 当永久事实。
为何 Mongo？事实和标签的结构随来源变化，嵌套证据适合文档模型；同时为 chain/address/direction/block 等查询建立索引，不能只依赖灵活 schema。

常见失分表述与改写

不要说改为
“我通过 tx.to 知道用户 swap 了。”“tx.to 和 calldata 表示入口意图；我解析成功 receipt，并验证 Pool emitter/factory 后确认成交事实。”
“图证明了赃款流向。”“图展示已采集范围内的资金事实关联，不做逐币归因或身份定论。”
“Etherscan 就是链。”“Etherscan 是索引服务；协议层数据由节点 RPC 和共识链提供。”
“Base 是 Ethereum。”“Base 是独立的 OP Stack L2；跨链关系必须有两侧协议证据。”

故障场景演练

  1. 上游 429：限并发与退避，任务保留检查点，前端显示同步中或暂不可用，不伪造空结果。
  2. 同 tx 多条 Token 转账：以 logIndex 区分，避免 txHash 覆盖。
  3. Pool 看似 Swap：先过 ABI 形状，再用 factory() 验证协议身份；失败时降级为未验证日志。
  4. bridge 对端未查到：保持 observed/unknown，不凭金额时间生成跨链边。
