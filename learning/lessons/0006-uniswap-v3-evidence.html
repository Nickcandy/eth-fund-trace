AMM 与 V3 的最小模型

传统恒定乘积 AMM 用 x * y = k 描述储备关系；买入一种资产会改变两边储备和边际价格。Uniswap V3 将流动性限制到价格区间，因而资本效率更高，但成交、价格和流动性不再能只靠一对全局 reserve 直觉解释。项目不重算完整 AMM 状态，而是解析 Pool 产生的事件。

Swap event 怎么读

event Swap(address indexed sender, address indexed recipient,
  int256 amount0, int256 amount1, uint160 sqrtPriceX96,
  uint128 liquidity, int24 tick)

amount0/amount1 是 Pool 余额变化：正数表示 Pool 收到该 token，负数表示 Pool 发出。正常成交中它们应符号相反。因为是 int256，读取时必须按二进制补码转有符号数；直接当 uint256 会把负数读成巨大正数。

为什么只匹配 topic 不够

任何合约都可伪造相同 event 签名。分析器应依次检查：receipt 顶层成功、topics[0] 的 ABI 形状、topic/data 长度、signed amount 不变量、emitter 的 token0()/token1()/fee()，以及 factory() 是否为已知 Uniswap V3 Factory。最后一步把“长得像 Swap”提升为“来自该协议注册体系的 Pool”。

WETH 不是 ETH

原生 ETH 不遵循 ERC-20 接口。WETH 合约将 ETH 存入后记账并发出 Deposit，提取时发出 Withdrawal；随后 WETH 才能像普通 ERC-20 一样参与 Pool 与 Router 流转。解析时应同时验证 event signature 与 WETH 合约地址，不能把任意同名事件当作包装行为。

可靠输出与 MEV 边界

层级例子可信度
输入意图Router selector、path 参数可能失败或被复杂路由改写
事实成功 receipt 的 Transfer、Pool Swap、WETH log可定位到 logIndex/emitter
解释“完成了某个 V3 交易对成交”需要 factory 等身份验证
推断用户实际经济结果或 MEV 攻击需要退款、多跳和完整区块上下文

用户提交的是参数和约束，例如最低可接受输出量；最终成交价格来自执行时状态。仅凭一个 Swap log 不能宣称发生了夹子攻击。
