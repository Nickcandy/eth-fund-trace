从链上交易到资金图

本课只解决一个问题：你的系统展示的一条“资金边”究竟从哪里来，它能证明什么，又不能证明什么。

先记住结论

Ethereum 本质上是一个复制状态机。用户提交签名交易，EVM 执行它，区块记录交易顺序，receipt 记录执行结果和 logs。你的项目没有直接“读取一张资金流表”，而是从不同证据源恢复并规范化资金事实，再用图算法查询它们。

协议事实block、transaction、receipt、log、call trace
数据入口Etherscan account API 与 Ethereum JSON-RPC
规范化ETH、internal ETH、ERC-20 Transfer
事实存储MongoDB Transfer 与唯一证据键
解释层BFS 图、画像、风险、DEX、跨链桥

三类资金边为什么不能混为一谈

1. 普通 ETH 转账

交易本身有 from、to 和 value。这是顶层 message call 的 value，不包含合约执行过程中再次发送的 ETH。

2. Internal ETH

合约 A 调用合约 B 时可以携带 value。它通常需要执行 trace 或索引器加工才能恢复。所谓“internal transaction”是区块浏览器常用的数据产品术语，不是一个由私钥签名、进入 mempool 的独立 Ethereum transaction。

3. ERC-20 Transfer

Token 是合约中的状态。用户调用 Token 或 Router 后，Token 合约更新自己的账本，并按 ERC-20 规范发出 Transfer(address,address,uint256) 事件。ETH 的 value 与 ERC-20 的事件日志属于不同证据通道。

面试中的关键纠正：一笔 transaction 可以对应零到多条资金事实边。反过来，一条业务语义如 Swap 也可能由多条 Transfer、一个或多个 Pool Swap event 和 WETH 包装事件共同证明。

为什么唯一键不能只是 txHash

同一个交易中可能有多个 ERC-20 Transfer log、多个 internal call，甚至同一资产多次转移。项目使用近似如下的事实身份：

(chain, txHash, source, traceId, logIndex, asset)

chain 防止多链哈希空间混用；source 区分普通、内部和 Token 事实；traceId/logIndex 定位交易内证据；asset 防止跨资产合并。代价是上游合成的 logIndex 或 trace 标识必须稳定，否则重跑可能产生重复或错误覆盖。

一次地址追踪请求发生了什么

  1. HTTP 层校验 chain、地址、depth、direction 和资产过滤。
  2. Trace Manager 检查地址数据是否已同步；缺失时排入 Sync Job。
  3. Syncer 获取安全链头，分三类 action 拉取历史，按页保存检查点并批量 upsert。
  4. Tracer 从种子地址开始 BFS，查询入边/出边，按规则选择 Top-N 邻居并推进层级。
  5. 标签、画像和风险层基于已有样本输出解释；前端展示图和数据质量。

时间复杂度不能只写传统的 O(V+E)。纯 BFS 是 O(V+E)，但实际系统主要成本是外部同步。若深度为 D、每层最多展开 F 个地址、每地址三类接口各读取 P 页，则 API 请求上界约为 O(3PFD)；没有预算时，高频地址的全历史会支配延迟与成本。

面试追问与可靠回答

“为什么不用节点 RPC 直接查一个地址的全部历史？”

标准 JSON-RPC 擅长按块、哈希、状态和日志读取，但没有通用的“列出地址全部普通交易/内部调用历史”接口。要么扫描区块并自建索引，要么依赖 Etherscan 这类索引服务。当前 Demo 选择后者换取开发速度，代价是配额、分页上限、第三方正确性和可用性依赖。

“为什么 transaction 成功还不够？”

transaction 表达意图和入口；receipt 的 status 说明顶层执行是否成功，logs 才承载 Token/协议事件；内部 call 仍可能需要 trace。协议分析必须组合证据，而不是根据 calldata 或 to 地址猜结果。

“你的图能证明赃款最终去了哪里吗？”

不能做强因果或逐币归因。它证明的是已采集窗口内存在链上资金事实和协议关联。账户余额具有可互换性，交易所、Mixer、Router、跨链桥和批处理会打断简单归因；Top-N、窗口截断和上游数据缺失也会导致 partial。
