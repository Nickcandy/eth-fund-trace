Lesson 0001约 25 分钟

从转账事实到可解释的资金图

本课的目标不是背代码，而是能用一个统一模型回答：怎么搜、怎么扩、在哪里停、遇到合约怎么解释。

先建立总模型

1. 采集Etherscan 地址历史与 Ethereum 单笔交易事实
2. 标准化normal、internal、ERC-20 统一为 Transfer
3. 搜索按资金状态做分层图扩展
4. 解释合约节点回到 entry transaction 解析协议
5. 停止终点、证据不足、缺数据或资源保护

面试开场可以先说：“这个项目不是从一个地址无限爬邻居，而是在固定数据覆盖内，对带资产、金额和时间边界的资金状态做确定性扩展。”这句话同时解释了为什么普通 BFS 不够。

一、搜索：BFS 的节点其实是资金状态

初始地址经过校验和覆盖检查后，生成一个或两个方向的状态。direction=both 会拆成 in 和 out 两条 frontier。代码按层处理当前 frontier，生成 next frontier，因此遍历形态是 BFS。

state = {
  address, direction,
  assetMode, asset,
  amount, anchorBlock,
  enteringTx, path
}

真正重要的是状态维度：

  • asset 防止把 USDT 的来路接到 ETH 的去向。
  • amount 是可归因预算，避免一笔 10 ETH 的收入解释出 100 ETH 的后续支出。
  • anchorBlock 建立因果时间窗口：向下游只看进入之后，向上游只看进入之前。
  • enteringTx 是合约语义解析锚点；同一个合约的不同交易不能混在一起。
  • path 用于发现当前路径环路。

候选事实经过四层过滤：资产受支持、金额为正、达到代码门槛、仍有分支预算。下游按区块从早到晚，上游从晚到早；每条边最多消费剩余预算。这近似 FIFO/反向 FIFO 的可重复归因。

边界：Ethereum 是账户余额模型，没有 UTXO 那样的“某一枚币”。这里得到的是有时间和金额约束的可审计归因，不是数学上唯一的逐币流向。

检索 1：visited[address] 足以完成本项目去重。

二、扩展：EOA 扫时间窗口，合约解析单笔交易

EOA 扩展

先检查该地址的 normal/internal/token 三类覆盖是否包含所需时间窗口。如果没有，Graph.Trace 返回 AddressNotSyncedError；任务管理器捕获后创建同步任务，等待完成，再从根地址重跑。第二次仍无法取得覆盖，才把该依赖标为 missing_data 并返回 partial 结果。

同步写入采用批量 upsert；各 Etherscan action 的检查点只在事实写入成功后推进。这样重试不会重复制造边，也不会把“抓取过”误写成“数据完整”。

合约扩展

合约地址的全历史通常巨大而且语义混杂，因此不是继续查询“这个合约所有转账”。系统拿到进入边的 txHash，只分析那一笔 transaction：

entry transfer
  -> Analyze(chain, txHash)
  -> verified conversion(tokenIn, amountIn -> tokenOut, amountOut, recipient)
  -> 生成语义 Transfer
  -> 切换资产后继续扩展 recipient

只有 conversion 的状态、输入输出、金额和接收者都完整时才切换资产。否则终止为 ambiguous_conversion。这是避免“看到 Router 地址就猜它一定完成了 Swap”的关键设计。

人工扩展

前端对已有非终点节点发起一次单方向扩展。后端从根图入边恢复资产、总金额、最早/最晚区块和路径，只查询一跳，再把结果按节点键、边键和资金状态键合并。它适合调查员主动展开局部，不改变自动追踪的证据规则。

检索 2：到达 Swap Router 后，应优先解析进入它的单笔交易。

三、终点：业务终点、证据边界、数据边界、计算边界

不要回答“没有下一笔交易就是终点”，这只覆盖一种情况。更准确的分类是：

类别判断为什么停止
业务终点IsTerminal、交易所/热钱包标签、WOO X 钱包资金已进入定义好的归宿，不继续扩大图
协议边界已知 bridge 身份目标链不在当前通用追踪范围
证据边界未知合约或 conversion 不唯一继续会把猜测伪装成事实
数据边界补同步失败、高频地址当前数据不足或成本过高
自然边界窗口内无匹配 transfer、零地址没有可继续消费的正金额事实
计算边界路径环路、5,000 节点保证任务有界；保留已确认的到达边

一个节点可以因为工程保护成为终点，但这不意味着它具有风险。风险模块目前只看查询地址自身的确定性标签，不做“和坏地址交易过，所以也是坏地址”的传播。

检索 3：high_frequency 是停止扩展原因，不是风险标签。

四、协议解析：topic 识别只是第一步

解析器采用“事实 → 解码 → 身份验证 → 一致性验证 → 质量状态”的流水线。分析结果按 (chain, txHash) 缓存，并用 AnalysisVersion 使规则升级后旧缓存失效。

Uniswap V3 示例

  1. Receipt 必须成功，遍历 logs，按 topic0 识别 Transfer、WETH 和 V3-shaped Swap。
  2. Swap data 的前两个 word 按二进制补码解析为有符号 int256；一正一负才符合交换形态。
  3. 正值代表 Pool 收到的输入，负值绝对值代表 Pool 发出的输出。
  4. 不能仅凭相同 event topic 认定 Uniswap。对 log emitter 调用 token0()、token1()、fee()、factory()；factory 必须等于官方 V3 Factory。
  5. 再用 ERC-20 Transfer logs 从 Pool 输出沿交易内转发链寻找唯一接收者；分叉、循环、未知 Router 落点都会使 route ambiguous。

官方定义明确指出，amount0/amount1 是 Pool 的 token0/token1 balance delta，而不是用户余额变化。这是符号方向的依据。

其他协议

  • WETH：同 topic 还不够，emitter 必须是官方 WETH 地址。
  • KyberSwap RFQ：校验 Router/Executor、Transfer、internal ETH call 或 WETH withdrawal funding 的一致性。
  • THORChain/MAYAChain：按 selector 和 ABI offset 解动态 memo，提取 vault、asset、amount、destination。THORChain 的特定跨 BTC 路径继续用协议 API 和 Bitcoin 输出验证真实出站。
  • BitTorrent Bridge：同时匹配函数输入、LockedEther 与 StateSynced；因为目标链执行未验证，仍标 partial。
通用扩展方式：新增协议时实现独立 adapter：声明支持的合约身份、事件/函数 ABI、必需证据、输出 conversion 和失败原因；不要把协议分支继续堆进通用 BFS。

五分钟口述模板

第一分钟，数据层：“Ethereum RPC 没有按地址枚举完整历史的标准接口，所以地址历史通过 Etherscan 的 normal/internal/token 三类 API 同步；单笔协议语义再查 transaction、receipt、logs 和必要的 contract calls。写库是幂等的，三类覆盖和检查点独立维护。”

第二分钟，搜索层：“搜索是分层 BFS，但状态不是单个地址，而是地址、方向、资产、可归因金额、进入区块和进入交易。下游只看进入后，上游只看进入前，按时间消费金额预算，避免资金被重复放大。”

第三分钟，扩展层：“普通 EOA 缺数据时先同步需要的窗口再重跑；合约不扫全历史，而是解析进入它的交易。如果能从 receipt 和协议身份得到唯一 conversion，就切换到输出资产和接收地址继续，否则保留到达事实并停止。”

第四分钟，终止层：“终点分业务、协议、证据、数据和资源五类，例如交易所标签、跨链桥、未知合约、高频地址、环路和 5,000 节点保护。终点是计算边界，不等于风险标签。”

第五分钟，协议与 trade-off：“以 Uniswap V3 为例，我不仅匹配 Swap topic，还解有符号 amount0/amount1，再读取 pool 的 token0/token1/factory 验证官方身份，并用 Transfer logs 解唯一接收者。整个系统优先低误判和可审计性，代价是协议覆盖有限、账户模型归因不是逐币证明。”

高概率追问

追问回答要点
为什么不用 DFS？BFS 便于按距离增量返回、统一节点预算和稳定复现；但真正正确性来自状态维度和金额/时间约束，不来自 BFS 本身。
复杂度是多少？图算法部分约 O(V + E log E)，排序来自各 frontier/候选；空间 O(V + E)。实际瓶颈是外部 API、Mongo 查询和高扇出，不是内存队列。
怎么避免重复和环？Transfer 唯一键幂等 upsert；状态键防重复入队；path 防当前路径闭环；结果合并有 node/edge/money-state key。
链重组怎么办？当前依靠确认数或固定快照降低风险，但缺少生产级 reorg 回滚。生产应保存 block hash，在重组窗口内重验并回滚受影响事实和缓存分析。
如何新增协议？用 adapter/registry 隔离 ABI、身份和证据规则；输出统一 conversion，不改搜索器。补 fixtures、失败交易、伪造 topic、代理/升级和多跳歧义测试。
项目最大局限？索引数据不等于完整 execution trace；白名单资产和协议覆盖有限；资金归因是启发式；通用跨链目标链没有覆盖。

代码与文档不一致，如何回答

直接说当前实现，不要替设计文档辩护：

  • 当前代码只自动保留 ETH 与 DAI/USDC/USDT/WETH，并过滤小于 0.01 ETH、50 USDT 的 Ethereum 主网边。
  • 同步默认每 action 5 万条，另有 20 万条硬保护；Trace 单次查询上限为 5 万条。
  • 当前 depth 被归一化为 0，不是固定跳数。

可以补一句：“这暴露了文档与行为契约没有自动校验的问题；我会把阈值和支持矩阵放进配置/公开能力接口，并用契约测试生成文档。”
