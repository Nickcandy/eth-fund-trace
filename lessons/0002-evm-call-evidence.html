先记住执行模型

EVM 不是“读取交易描述然后自动转币”。它从交易的 to 找到目标账户；若目标有 code，就用 input/calldata 作为只读输入执行字节码。执行可能读写 storage、产生内部 call、转移 ETH、发出 logs，最后成功提交状态或因异常回滚。

验证交易签名、nonce、余额、费用字段、gas limit
建立调用to、value、calldata 与初始 gas
执行字节码stack、memory、storage、call frames
形成结果return data、logs、gas used、status
提交或回滚成功提交；未捕获异常回滚状态

边界：receipt 是顶层交易的最终结果摘要，不包含完整内部调用树；要回答“Router 内部又调用了谁”，通常还需要 trace。

calldata：EVM 收到的输入

Solidity ABI 下，函数调用的 calldata 由两部分组成：

0x | 4-byte function selector | ABI-encoded arguments

selector = first4bytes(keccak256("functionName(type1,type2,...)"))

例如 ERC-20 transfer(address,uint256) 的 selector 是 0xa9059cbb。地址和整数通常各占一个 32-byte word；地址是 20 bytes，因此左侧补零。动态类型不是直接把内容放在参数槽位，而是先放相对偏移，再在 data 区保存长度和内容。

你代码里的零参数调用

poolMetadata 使用四个 selector 调用候选 Pool：

calldata函数返回值目的

0xd21220a7token1()ABI address word读取第二种 Token
0xddca3f43fee()ABI uint word读取 V3 费率档

这里调用的是 eth_call：节点在给定区块状态上模拟执行并返回 bytes，不生成链上 transaction，也不支付真实 gas。你的客户端目前使用 latest，工程上意味着结果依赖查询时链头；对历史审计，更严谨的做法是使用交易所在的 block number。

event log：EVM 留下的结构化证据

一个 log 包含 emitter 合约地址、最多 4 个 topics 和任意长度 data。对非 anonymous event：

topics[0] = keccak256("EventName(canonicalTypes,...)")
topics[1..] = indexed 参数
data = ABI 编码的 non-indexed 参数

ERC-20 Transfer 对照代码

event Transfer(address indexed from, address indexed to, uint256 value)

log.address = Token 合约地址
topics[0]   = Transfer event signature hash
topics[1]   = from，左侧补零到 32 bytes
topics[2]   = to，左侧补零到 32 bytes
data        = value，一个 uint256 word

因此 parseTransfer 从 emitter 得到 Token，从两个 topics 取地址，从 data 取金额。topicAddress 保留 64 个 hex 字符的最后 40 个字符，正是从 ABI word 中取 20-byte address。

为什么 topic 匹配还不够

任意合约都能声明同签名事件。事件 signature 只说明日志形状，不证明 emitter 是官方协议。你的 WETH 解析额外验证 log.address == WETH；Uniswap 解析则继续对 emitter 执行 factory() 并要求返回官方 V3 Factory。这是“语法匹配”到“协议身份验证”的升级。

有符号整数：为什么 Swap 不能都按 uint256 读

Uniswap V3 Swap 的 amount0 与 amount1 是 Pool 余额变化，类型是 int256。正数表示 Pool 收到，负数表示 Pool 发出；正常 Swap 两者符号相反。负数在 32-byte word 中使用二进制补码编码。

若最高 bit 为 0：value = raw
若最高 bit 为 1：value = raw - 2^256

项目中的 signedWord 必须执行这一转换；若直接按 uint256 解码，负数会变成极大的正数，Token 方向和金额都会错误。代码再用 amount0.Sign()*amount1.Sign() == -1 检查基本事件不变量。

gas：执行资源，不是转账金额

gas 是计算资源单位，gasLimit 是本次交易允许消耗的上限。EIP-1559 常见费用近似为：

effectiveGasPrice = min(maxFeePerGas, baseFeePerGas + maxPriorityFeePerGas)
actualFee         = gasUsed * effectiveGasPrice
  • baseFee 由协议决定并销毁。
  • priority fee 是给验证者的 tip。
  • maxFeePerGas 是用户愿意支付的单价上限，不是必然支付额。
  • 执行成功但业务结果差，仍会付费；执行 revert 也会为已经消耗的计算付费。

revert：原子回滚不等于什么都没发生

未被上层捕获的异常传播到顶层时，交易 status=0，本次交易产生的状态写入、Token 余额变化和 logs 都不会作为成功结果提交；但 transaction 和失败 receipt 会留在链上，nonce 已消耗，gas 费用也已支付。

必须注意调用层级：合约可以通过低级 call 或 try/catch 捕获子调用失败并继续执行。如果顶层最终成功，receipt 可以是 status=1，而某个内部 call 仍然失败。这也是 receipt 无法替代 trace 的原因。

情况状态效果gas项目应如何解释
顶层成功提交最终状态与 logs支付 gasUsed继续解析 receipt logs
顶层 revert本交易状态和 logs 回滚仍支付已用 gasSucceeded=false，不构造成功 Swap
子调用失败且被捕获子调用回滚，外层可继续失败调用仍耗 gas仅看 receipt 无法完整说明内部过程
eth_call revert不提交任何链上状态调用者不付链上费用RPC 返回 error/revert data，不能当作空值

从代码看证据等级

  1. TransactionByHash 给出入口地址、value 和 calldata，只表示调用输入。
  2. TransactionReceipt 给出顶层 status 与 logs，确认执行结果。
  3. topics[0] 匹配判断日志是否具有某种 ABI 形状。
  4. 检查 log emitter、数据长度和符号不变量，过滤畸形候选。
  5. 对 Pool 调用 factory()，确认 emitter 属于官方 Uniswap V3 Factory。
  6. 证据不完整时输出 partial 或 Verified=false，而不是猜测。
