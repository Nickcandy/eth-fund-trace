0. 先解决“地址”

Ethereum 地址在界面上通常都是同一种格式：0x 加 40 个十六进制字符，也就是 20 bytes。只看字符串外观，无法判断它是用户账户还是合约。

概念谁控制能否主动发起普通交易收到调用时会怎样
传统 EOA私钥持有人可以签名发起通常只是收 ETH，不执行合约字节码
合约账户部署在地址上的 code不能凭空主动签名；由交易/调用触发EVM 执行该地址的 code
智能合约钱包合约规则、owner/key/module通常通过 EntryPoint 或外部交易驱动执行钱包合约逻辑
EIP-7702 EOA仍有 EOA 私钥，同时委托代码可以可能执行被委托的代码

工程上怎么判断

  1. 调用 eth_getCode(address, blockTag)。
  2. 返回 0x：该区块上没有代码，通常作为传统 EOA 候选。
  3. 返回普通 bytecode：通常是合约账户。
  4. 返回 EIP-7702 delegation indicator：这是带代码委托的 EOA，不能直接标成传统合约。

必须带区块高度理解结果：同一个地址在部署合约前可能没有 code，部署后才有。还有 precompile 等特殊地址。因而“EOA/contract”是链上状态与行为分类，不是地址字符串的一部分。

钱包不等于地址：MetaMask 是管理密钥、构造和签名交易的软件；EOA 是链上的账户；地址只是账户标识。一个钱包应用可以管理多个 EOA，也可以操作智能合约钱包。

2. 示例二：直接调用 USDT.transfer

在 Etherscan 打开这笔主网交易

这笔交易最重要的地方是出现了三种不同角色的地址：

交易 From        0x978e...3456  用户/签名者
交易 To          0xdac1...1ec7  USDT 合约
Token 收款地址   0xd5cf...7c30  transfer 函数参数

交易的 To 不是 USDT 的最终收款人。交易发给 USDT 合约，请它执行内部账本转移；真正收款人编码在 calldata 中。

完整 calldata

0xa9059cbb
000000000000000000000000d5cff405d70a4ba449df091f54ab6e4769b67c30
000000000000000000000000000000000000000000000000000000001d2c7dec
片段含义
0xa9059cbbtransfer(address,uint256) 的 4-byte selector
第一个 32-byte word收款地址；取最后 40 个 hex 字符得到 0xd5cf...7c30
第二个 32-byte word原始数量 0x1d2c7dec = 489455084

USDT 的 decimals=6，所以显示数量是 489455084 / 10^6 = 489.455084 USDT。transaction 的 value=0，因为这里没有发送 ETH；Token 数量存在 USDT 合约自己的 storage 里。

执行成功后 receipt 中的 Transfer log

log.address = 0xdac17f...1ec7                 // USDT 合约
topics[0]  = 0xddf252...b3ef                 // Transfer 事件签名
topics[1]  = 0x000...978e75381d64...3456     // from
topics[2]  = 0x000...d5cff405d70a...7c30     // to
data       = 0x000...000000001d2c7dec          // amount

calldata 表示“调用者要求执行什么”；receipt log 表示“合约成功执行后声明发生了什么”。你的项目使用后者构造 ERC-20 Transfer 事实。

4. selector 和 calldata 到底是什么

selector：函数编号

合约 bytecode 里可能有很多函数。EVM 收到一段 bytes，需要先知道你想调哪一个。Solidity ABI 约定：取规范函数签名的 Keccak-256 hash 前 4 bytes。

函数签名：transfer(address,uint256)
Keccak-256：a9059cbb...（后面省略）
selector： 0xa9059cbb

selector 只有 4 bytes，理论上可能碰撞，所以它不是全球唯一身份证。正确解码还需知道目标合约 ABI。

calldata：整份调用参数包

calldata 是一次 message call 的只读输入 bytes。对常规 Solidity ABI 调用：

calldata = selector + ABI 编码后的全部参数

所以两者不是并列关系，而是selector 通常是 calldata 的前 4 bytes。没有参数的 token0() 调用，其 calldata 就只有 selector：0x0dfe1681。

ERC-20 合约的常见函数

函数是否改状态含义
totalSupply()否Token 原始总供应量
balanceOf(owner)否读取 owner 的原始余额
transfer(to, value)是调用者把自己的 Token 转给 to
approve(spender, value)是授权 spender 最多代扣多少 Token
allowance(owner, spender)否查询剩余授权额度
transferFrom(from, to, value)是spender 使用 allowance 从 from 转给 to

approve 不会立即把 Token 转走，只修改 allowance；后续 Router 常通过 transferFrom 扣款。无限授权会扩大合约被攻击或授权钓鱼时的损失范围。

6. 开源合约从哪里开始看

  1. OpenZeppelin IERC20.sol：最短，先看函数和 event 声明。
  2. OpenZeppelin ERC20.sol：看 transfer、approve、transferFrom 最终如何更新余额和 allowance。
  3. Uniswap V3 Pool Events：重点看 Swap 的 indexed 参数和 int256 amount0/amount1。
  4. UniswapV3Pool.sol：完整 Pool 实现，现阶段只定位 swap 和 emit Swap，不要从头硬读。
  5. Uniswap V3 SwapRouter.sol：看 Router 如何调用 Pool，而不是自己保存流动性。

一手资料

Ethereum Accounts 解释 EOA 与合约账户；ERC-20 定义函数和事件；Solidity ABI Specification 定义 selector、calldata、topics 和 data；EIP-7702 是“有 code 不一定是传统合约账户”的现代例外。

建议先只看示例一和示例二，确认能区分 ETH 转账与 Token 合约调用，再看聚合 Swap。任何字段不明白，直接贴 Etherscan 上的字段名即可继续解释。
