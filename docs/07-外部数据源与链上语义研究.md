# 外部数据源与链上语义研究

> 研究日期：2026-08-23  
> 适用范围：Ethereum Mainnet、Base Mainnet，以及本项目的 Etherscan V2 适配、资金边、地址画像和分层追踪。  
> 资料原则：下文的协议/API事实只引用官方一手资料；“项目建议”是基于这些事实的工程推论，不代表外部服务的承诺。

## 1. 结论摘要

1. Etherscan V2 的 `txlist`、`txlistinternal`、`tokentx` 都是“按地址和可选区块区间返回历史列表”的分页接口，支持 `page`、`offset` 和 `sort=asc|desc`。接口页面没有把 10,000 条声明为永久的服务端硬上限；本项目的 `page=1..100`、`offset=100`（最多 10,000 条/查询窗口）是客户端的保护性窗口。达到窗口上限后必须缩小区块范围继续查询，不能把内存结果丢弃后当作“没有数据”。
2. 以太坊的 ERC-20 转账是合约发出的 `Transfer` 日志事件；Etherscan 的 `tokentx` 返回的是 Token 转账事实，不能将 `contractAddress` 当作收款人，也不能将 ERC-20 事件当作 ETH internal transaction。
3. “内部交易”不是共识层单独收录的一笔签名交易。它是合约执行期间产生的内部 message/call；要从某个 `txHash` 还原调用树，优先使用交易 receipt 的 `logs` 和节点的 trace API。Etherscan `txlistinternal?txhash=...` 是索引器提供的便利视图，不等同于一个新的 L1/L2 交易。
4. `eth_getTransactionByHash` 负责交易本体，`eth_getTransactionReceipt` 负责已挖出交易的执行结果、状态、创建地址和日志，`eth_getCode` 可在指定区块判断地址是否有合约代码。按交易哈希分析不能只依赖交易本体的 `to/value` 字段。
5. Base 是独立的 EVM Layer 2（chain ID 8453），L2 交易、L1 交易、存款和提款有不同的交易域与生命周期。跨链边必须保留源链、目标链、两端事实交易和桥合约/消息证据，不能仅凭同地址、同金额或相近时间推断一条桥接边。
6. 高频地址的主要瓶颈不是 BFS 算法本身，而是“为展开一个节点先从创世同步三类全历史数据”的数据获取策略。交互式追踪应使用有界样本、最近优先、地址/页/记录预算；完整归档应作为独立任务。

## 2. Etherscan V2 地址历史接口

### 2.1 共同查询参数

Etherscan V2 的地址历史接口在 `/v2/api` 上使用 `chainid` 选择网络，并要求 `module=account`、对应的 `action` 和 `address`。三个接口都定义了：

- `startblock`：查询起始区块；
- `endblock`：查询结束区块；
- `page`：分页页码；
- `offset`：每页记录数；
- `sort`：`asc` 表示最旧记录优先，`desc` 表示最新记录优先。

这些参数意味着可以通过二分区块区间来控制一个查询窗口的密度，也可以通过 `sort=desc` 优先拿到最近活动。`offset` 是请求参数，不应被解释成“服务端保证永远返回这么多条”。

来源：

- Etherscan `txlist`：<https://docs.etherscan.io/api-reference/endpoint/txlist.md>（访问日期：2026-08-23）
- Etherscan `txlistinternal`：<https://docs.etherscan.io/api-reference/endpoint/txlistinternal.md>（访问日期：2026-08-23）
- Etherscan `tokentx`：<https://docs.etherscan.io/api-reference/endpoint/tokentx.md>（访问日期：2026-08-23）

### 2.2 三类 action 的语义边界

| action | 官方接口语义 | 本项目应保存的事实 |
| --- | --- | --- |
| `txlist` | 指定地址的普通交易历史 | 顶层交易发送方、收款方、ETH `value`、交易状态；合约创建使用 receipt/索引字段补出创建地址 |
| `txlistinternal` | 指定地址的 internal transaction 历史；按 `txhash` 查询时返回该交易内的 internal transactions | 合约执行产生的 ETH call/create 边，保留 `traceId`、`type` 和错误字段 |
| `tokentx` | 按地址和/或 Token 合约过滤 ERC-20 transfer 历史 | `from`、`to`、Token `contractAddress`、原始整数 `value`、`tokenDecimal`；资产类型必须是 `erc20` |

`txlistinternal` 的按哈希接口明确说明只返回非零 value 的内部交易。这是一个索引器过滤规则，不应推广为“所有内部调用都有资金价值”。

来源：<https://docs.etherscan.io/api-reference/endpoint/txlistinternal-txhash.md>（访问日期：2026-08-23）。

### 2.3 “10,000 条限制”的准确解释

Etherscan 的接口文档公开了 `page` 和 `offset`，但没有在上述 endpoint 文档中声明一个固定的“每个地址最多 10,000 条”协议上限。当前项目的配置是：

```text
ETHERSCAN_PAGE_SIZE = 1000
ETHERSCAN_MAX_PAGES = 10
ETHERSCAN_INTERNAL_LOOKBACK_BLOCKS = 100000
SYNC_MAX_RECORDS_PER_ACTION = 100000
```

因此单次 `list(address, startblock, endblock, action)` 的客户端窗口最多读取 1,000 × 10 = 10,000 条原始记录。这与当前 Etherscan 错误响应的 `page × offset <= 10,000` 结果窗口约束一致；达到窗口后，客户端会按区块边界落库并继续切分。

Demo 默认只读取安全链头前最近 100,000 个区块的 `txlistinternal`。当 `SYNC_MAX_RECORDS_PER_ACTION` 大于零时，`txlist`、`txlistinternal` 和 `tokentx` 分别从新区块向旧区块读取最多指定条数，命中上限的地址和任务标记为 `partial/record_limit`；设为 `0` 则恢复不限条数的升序完整同步。停止或中断的任务只在同步模式和上限一致时复用 action checkpoint。

正确处理方式：

1. 记录达到 100 页时的最后一个原始 `blockNumber`；
2. 先将已经确定属于完整区间的记录批量 upsert；
3. 以该区块边界继续查询，必要时将区间二分；
4. 以原始响应条数判断分页结束，不能用过滤失败交易后的条数提前结束；
5. 对高频地址设置更高层的地址预算，达到预算后返回 `partial/high_volume_hub`，而不是静默失败。

### 2.4 服务额度与本地令牌桶

Etherscan 当前费率表把 Free、Lite 等计划分开：Free 为每秒 3 次、每日最多 100,000 次；Lite 为每秒 5 次、每日最多 100,000 次。实际可用额度取决于 API Key 所属计划和所查链。项目配置的 5 QPS 只表示本地进程的共享令牌桶目标，不会增加第三方账户的额度，也不覆盖多实例总量。

来源：<https://docs.etherscan.io/rate-limits.md>（访问日期：2026-08-23）。

工程约束：所有 action、`eth_blockNumber`、重试和并发任务必须共享同一个进程级 limiter；429/5xx/临时网络错误应有限重试并可被 Context 取消。每日额度需要独立的配额计数器和任务预算，不能只靠 QPS 限制解决。

## 3. Ethereum 账户、交易、receipt 与日志

### 3.1 EOA 与合约账户

Ethereum 官方账户文档区分两种账户：

- EOA（Externally-owned account）：由私钥控制，可以主动发起签名交易；
- Contract account：由部署的合约代码控制，没有私钥，只能在收到交易/消息后执行代码。

因此“交易量很高”不能直接等价于“热钱包”。一个高频地址也可能是 Token 合约、DEX Router、桥合约、批处理合约或交易所基础设施。`eth_getCode(address, block)` 返回 `0x` 时表示该区块没有合约字节码，才可将其作为 EOA 候选；判断必须注明区块高度。

来源：

- Ethereum accounts：<https://ethereum.org/en/developers/docs/accounts/>（访问日期：2026-08-23）
- Ethereum JSON-RPC `eth_getCode`：<https://ethereum.org/en/developers/docs/apis/json-rpc/>（访问日期：2026-08-23）
- Base 对 `eth_getCode` 的字段说明：<https://docs.base.org/base-chain/api-reference/ethereum-json-rpc-api/eth_getCode.md>（访问日期：2026-08-23）

### 3.2 交易本体与 receipt

官方 JSON-RPC 语义：

- `eth_getTransactionByHash` 返回交易本体；未知交易返回 `null`。`to=null` 表示合约部署交易；该对象不包含执行过程中所有内部 call。
- `eth_getTransactionReceipt` 返回已被纳入区块的交易 receipt；未挖出/未封存交易返回 `null`。receipt 包含 `status`、`contractAddress`、`logs` 等执行结果字段。

因此按 `txHash` 分析的最小读取链路应是：

```text
eth_getTransactionByHash(txHash)
  -> blockNumber/from/to/value/input
eth_getTransactionReceipt(txHash)
  -> status/contractAddress/logs
可选 debug_traceTransaction(txHash)
  -> 内部 call/create 调用树
```

来源：

- Ethereum JSON-RPC：<https://ethereum.org/en/developers/docs/apis/json-rpc/>（访问日期：2026-08-23）
- Base `eth_getTransactionByHash`：<https://docs.base.org/base-chain/api-reference/ethereum-json-rpc-api/eth_getTransactionByHash.md>（访问日期：2026-08-23）
- Base `eth_getTransactionReceipt`：<https://docs.base.org/base-chain/api-reference/ethereum-json-rpc-api/eth_getTransactionReceipt.md>（访问日期：2026-08-23）

### 3.3 Internal transaction 不是共识层交易

Ethereum 官方 glossary 将 internal transaction 定义为“从合约账户发送到另一个合约账户或 EOA 的 transaction”；同时把 message 描述为只在 EVM 内部传递、不会序列化的 internal transaction。Geth 官方 tracing 文档说明，EVM trace 是通过重新执行交易，收集实际执行的调用和 opcode 得到的。

工程上应使用更精确的名字：`internal_call`、`internal_create` 或 `execution_trace_edge`。它们共享外层交易哈希，但不拥有独立的共识层交易哈希、签名和 nonce。Etherscan 的 `txlistinternal` 是索引器把这些执行结果投影成列表，适合构建事实边，但不能与 `txlist` 的顶层交易计数混为一谈。

来源：

- Ethereum glossary：<https://ethereum.org/en/glossary/>（访问日期：2026-08-23）
- Geth EVM tracing：<https://geth.ethereum.org/docs/developers/evm-tracing>（访问日期：2026-08-23）
- Base `debug_traceTransaction`：<https://docs.base.org/base-chain/api-reference/debug-api/debug_traceTransaction.md>（访问日期：2026-08-23）

### 3.4 ERC-20 不是内部 ETH

ERC-20 标准要求成功的 `transfer`/`transferFrom` 触发：

```solidity
event Transfer(address indexed _from, address indexed _to, uint256 _value);
```

Token 合约还可以用零地址作为 mint 的 `from`，并要求零值转账也触发事件。这个事件位于 receipt 的 `logs`，其资产是某个 Token 合约的整数余额变化，不是外层交易的 ETH `value`，也不是内部 call 的 ETH `value`。

因此项目必须保持以下维度独立：

```text
assetType = eth | erc20
asset     = ETH 或 Token contract address
source    = txlist | txlistinternal | tokentx | rpc_receipt | trace
```

同一交易可能同时产生 ETH、内部 ETH 和多个 ERC-20 日志；不能按 `txHash` 把它们合成一条跨资产金额边，也不能把 `tokentx.contractAddress` 当成收款地址。

来源：<https://eips.ethereum.org/EIPS/eip-20>（访问日期：2026-08-23）；Ethereum smart contract events/logs：<https://ethereum.org/en/developers/docs/smart-contracts/anatomy/>（访问日期：2026-08-23）。

## 4. Base L2 与跨链边界

### 4.1 独立链域

Base 官方文档将 Base 定义为 EVM-compatible Layer 2；Base Mainnet 的 chain ID 是 8453，独立 RPC 和独立区块空间。Etherscan V2 也要求通过 `chainid` 选择查询网络。相同的 `0x` 地址在 Ethereum 与 Base 上不是同一条账本事实，必须用 `(chain, chainId, address)` 作为地址身份。

来源：

- Base 网络连接信息：<https://docs.base.org/base-chain/quickstart/connecting-to-base.md>（访问日期：2026-08-23）
- Base 协议概览：<https://docs.base.org/base-chain/specs/protocol/overview.md>（访问日期：2026-08-23）
- Etherscan V2 `txlist` 的 `chainid` 参数：<https://docs.etherscan.io/api-reference/endpoint/txlist.md>（访问日期：2026-08-23）

### 4.2 存款与提款不是普通同链转账

Base 官方 bridging 文档说明：

- Deposit 从另一条链发起，并在 Base 上派生为特殊的 L2 deposit transaction；它没有普通 EIP-155 交易的签名、nonce 和费用字段。
- Standard withdrawal 在 Base 上发起，之后在 Ethereum 上 prove，经过 challenge period 后在 Ethereum 上 finalize。
- 存款和提款使用跨域消息/桥合约，生命周期跨越两个链域。

因此跨链关系至少需要保存：

```text
sourceChain/sourceTxHash/sourceBlock
targetChain/targetTxHash/targetBlock（若已出现）
bridgeContract 或 messenger
message/withdrawal/deposit evidence
status = initiated | proven | finalized | unknown
```

只看到两个链上地址相同、金额相同或时间接近，不能生成桥接事实边。对于 Base，标准桥还涉及 `OptimismPortal`、`L2ToL1MessagePasser` 和 `L2StandardBridge` 等特定协议对象，必须把证据来源写入结果。

来源：

- Base Bridging and Withdrawals：<https://docs.base.org/base-chain/network-information/bridging-and-withdrawals.md>（访问日期：2026-08-23）
- Base Deposits specification：<https://docs.base.org/base-chain/specs/protocol/bridging/deposits.md>（访问日期：2026-08-23）
- Base Withdrawals specification：<https://docs.base.org/base-chain/specs/protocol/bridging/withdrawals.md>（访问日期：2026-08-23）

### 4.3 Base 的追踪能力与限制

Base RPC 文档提供标准 `eth_getTransactionByHash`、`eth_getTransactionReceipt`、`eth_getCode`，也提供需要启用 debug API 的 `debug_traceTransaction`。官方明确提示 debug tracing 会重新执行交易、计算成本高、可用性和速率受节点提供方影响，不能放在每个地址同步或 BFS 热路径中。

Base 公开 RPC 端点也明确标注有速率限制，不适合生产流量；生产环境应使用节点服务商。Demo 阶段可把 RPC trace 作为“指定 txHash 深入分析”的可选能力，而不是用它扫描所有地址历史。

来源：

- Base `debug_traceTransaction`：<https://docs.base.org/base-chain/api-reference/debug-api/debug_traceTransaction.md>（访问日期：2026-08-23）
- Base 连接与公开端点说明：<https://docs.base.org/base-chain/quickstart/connecting-to-base.md>（访问日期：2026-08-23）

## 5. 对本项目的直接设计建议

### 5.1 如何加速追寻一个地址

建议将“交互式追踪”和“完整归档”拆开：

```text
交互式追踪：最近优先 + 有界区块窗口 + 每地址预算 + Top-N
完整归档：异步、可暂停、可恢复、独立配额
```

交互式追踪的默认策略：

- `sort=desc`，先取最近交易；
- 每个地址限制 action 页数、记录数和耗时；
- 三类 action 可分别达到预算，结果标记 `partial`；
- 已达到预算的地址标为 `high_volume_hub`，保留已取得事实边并停止 BFS 扩展；
- 只为种子和真正进入 Top-N 的邻居发起同步；
- 以 `txHash` 为锚点时，上游和下游使用不同的区块方向，并强制路径区块单调性；
- 使用 receipt logs 识别 Token 事实，使用 trace 识别内部 call，而不是把所有 action 合并。

复杂度上，若每层最多展开 `F` 个地址、每个地址只读取预算 `P` 页、追踪深度为 `D`，API 页面上界是 `O(P * F * D)`（还要乘以 action 数量）；空间复杂度主要由已访问地址和保留事实边决定。相比全历史同步，这个上界可解释、可取消，也能给前端显示进度。

### 5.2 如何判断“热钱包”

不要把工程截断分类和风险画像混为一谈：

```text
high_volume_hub       数据规模/同步保护分类
suspected_hot_wallet  基于有限或完整样本的行为推断
exchange_hot_wallet   需要人工或可信公开证据的确定性标签
```

建议的 `hot-wallet-v2` 输入：

- `eth_getCode` 在目标区块返回 `0x` 的 EOA 候选；
- 最近固定窗口内的入账数、出账数、活跃天数和独立对手方；
- 归集（多发送方汇入后转出）与批量分发（收到后向多接收方转出）；
- 样本是否被页/记录预算截断。

输出必须带 `dataStatus=complete|partial`、样本窗口和规则版本。若只有“交易数很多”，最多输出 `high_volume_hub`，不能输出 `suspected_hot_wallet`。

### 5.3 碰到单个节点交易过多怎么办

处理顺序建议为：

1. 给地址设置硬预算（页数、记录数、耗时、任务总 API 页数）；
2. 先按最近交易取样，避免从创世区块升序扫描；
3. 达到预算时持久化已成功的批次，状态为 `partial`，记录截断原因；
4. 保留连接到高频节点的事实边，但停止向其外扩；
5. 画像只声明“基于截断样本”，不自动升级为热钱包；
6. 用户明确请求时再排队完整归档；
7. 对重复读取使用 Mongo upsert/唯一键，避免区间二分造成重复事实。

这套策略把“结果尽快可看”和“数据完整可审计”分成两个目标，不会因为一个交易所/路由器/批处理地址阻塞整个 BFS。

### 5.4 按 txHash 追踪的最小实现

按交易哈希追踪不应只传一个 `startBlock` 给地址同步器。推荐流程：

1. 在目标链用 `eth_getTransactionByHash` 取交易本体；
2. 用 `eth_getTransactionReceipt` 校验已落块、执行状态、合约创建地址和 ERC-20 日志；
3. 对内部 ETH 调用，在 Etherscan 使用 `txlistinternal&txhash=...` 或在自有/支持的节点调用 `debug_traceTransaction`；
4. 以锚点区块切分方向：上游只接受不晚于锚点的边，下游只接受不早于锚点的边；
5. 资产维度独立保留；同一哈希中的 ETH、internal ETH、ERC-20 不合并成跨资产边；
6. 结果记录 `source=rpc_receipt|etherscan_internal|rpc_trace` 和证据完整度。

## 6. Demo 阶段必须显式展示的状态

前端/HTTP 结果应区分以下状态，避免用户把“空结果”理解成“没有风险”：

- `complete`：请求区间和 action 都完成；
- `partial`：达到地址或任务预算，保留样本但不代表全历史；
- `high_volume_hub`：因数据量过大停止扩展；
- `awaiting_receipt`：交易哈希已知但尚未有 receipt；
- `trace_unavailable`：当前节点不支持/未授权 debug trace；
- `cross_chain_unverified`：看到了疑似两端活动，但缺少桥/消息证据；
- `chain_mismatch`：请求链与数据链不一致，拒绝合并。

这些状态属于数据质量和证据等级，不应直接映射为风险等级。风险评分仍需使用版本化规则，并把交易哈希、日志索引、trace 路径或桥接消息作为证据。
