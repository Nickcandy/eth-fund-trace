# 项目难点与解决方案

## 1. 核心问题

这个项目最难的不是把转账画成图，而是在以下约束同时存在时保持结果可信：

- 外部地址索引服务有分页窗口、QPS、每日额度和故障；
- 一个高频地址可能拥有数十万到数百万条资金事实；
- ETH、内部 ETH、ERC-20、Swap 和 Bridge 的证据语义不同；
- TopN、深度和任务预算会漏掉未进入候选集的关系；
- 账户制链只能证明交易关系，不能证明同一单位资金的连续流向；
- 标签、风险分数和实体归属都可能因数据水位或规则版本变化。

因此系统目标不是声称“全量且确定”，而是在已知数据水位和预算内返回可解释、可审计、明确标注完整度的结果。

## 2. 地址历史采集

### 难点

普通 ETH、内部 ETH 和 ERC-20 来自不同接口。分页失败、区块边界重读和服务重启可能造成漏数或重复；只用交易哈希去重，又无法区分同一交易内的多条 Trace 和 Log。

### 当前解决

- 将 `txlist`、`txlistinternal`、`tokentx` 标准化为统一 `Transfer`；
- 使用 `(chain, txHash, source, traceId, logIndex, asset)` 作为事实唯一键；
- 每页标准化后执行 MongoDB 无序批量 upsert；
- 只有事实写入成功后才推进检查点；
- 使用确认数计算安全链头，并支持内部交易回看窗口；
- 保存页数、读取数、写入数、区块区间和拆分次数；
- 对限流、临时上游故障和不可重试错误分类，错误向任务层传播。

### 仍有边界

当前数据完整度受 Etherscan 地址索引和配置窗口约束。确认数只能降低短重组风险，不能代替保存区块哈希后的重组检测、回滚和重放。同步与 Trace 仍可能在交互请求之后触发高频邻居的长时间历史同步。

一次真实运行中，第一层高频邻居产生了约 87 万条唯一事实和约 8,800 页请求。这说明交互式查询与完整归档必须在生产环境拆成不同工作负载。

## 3. 百万级对手方聚合

### 难点

TopN 的正确语义是“累计金额最大的 N 个对手方”，不是“金额最大的 N 笔交易”。如果先读取所有交易再构造 `map[address][]Transfer`，内存会随交易数增长；百万级地址很容易产生较大的堆占用和 GC 压力。

链上金额以最小单位十进制字符串存储，也不能用 `float64` 排序。

### 当前解决

`TopCounterparties` 对单个父地址、单个方向和单个资产执行一次查询：

1. 使用 `(chain, endpoint, asset, counterparty)` 复合索引；
2. MongoDB 只投影对手方、金额和必要元数据，并按对手方排序；
3. Go 使用 `big.Int` 累加当前连续分组；
4. 每个分组结束时只向固定大小的小根堆提交汇总；
5. 最终按累计金额降序、金额相同时按对手方地址升序返回。

内存复杂度为 `O(TopN)`，而不是 `O(交易数)`。同一对手方的全部交易会进入 `totalAmount` 和 `transferCount`，前端直接展示后端汇总结果，不再二次聚合。

关系内的合约转换也只保留金额最大的 20 笔交易，临时聚合结构被这个常量约束。

### 仍有边界

有界内存不代表常数查询时间。当前查询仍需扫描匹配资产下的全部事实，时间复杂度与匹配记录数线性相关。MongoDB 索引避免了无关集合扫描，但高频地址仍需要通过 `explain("executionStats")`、真实分布压测和 P95/P99 指标判断是否需要增量聚合桶。

## 4. 图扇出、TopN 与环路

### 难点

单向 `depth=3, topN=10` 的理论节点数已达到：

```text
1 + 10 + 100 + 1000 = 1111
```

双向追踪、高频 Router、桥和交易所热钱包会进一步放大图。固定 TopN 还可以被拆单规避：大量小额对手方可能全部排在主要金额关系之外。

### 当前解决

`trace-v5` 使用分层 BFS，并采用以下边界：

- 上游和下游分别展开；
- TopN 对每个父节点、每个方向、每个资产独立计算；
- 对手方先累计同资产全部金额和笔数，再按金额选 TopN；
- 搜索状态包含地址、方向和资产，避免不同资产分支互相误删；
- 已访问状态去重，确定性终点保留到达边但不继续展开；
- 最大深度为 5，总访问节点硬上限为 5,000；
- 自转事实可保留，但风险传播不让它占候选配额或继续展开。

根节点追踪原生 ETH 和官方 Token 白名单。普通地址沿当前资产继续；只有验证通过的协议转换才能切换资产。

### 仍有边界

TopN 是展示和搜索预算，不是风险检测的完整输入。它能保留主要金额关系，但会漏掉频繁小额、新近关系和大规模分散转账。系统因此将展示 Trace 与风险传播分离；尚未实现的高扇出行为分析则记录在 [Demo 边界与生产化](03-Demo边界与生产化.md)。

## 5. 链上语义与协议证据

### 难点

以下对象不能当成同一种“转账”：

- ERC-20 是合约 `Transfer` Log；
- 内部 ETH 是执行 Trace 中的 value movement；
- Swap 需要 Router、Pool、Token 输入输出和 Receipt 共同解释；
- Bridge 需要两条链上的协议消息对应；
- 交易所、攻击者等身份需要外部证据，无法只靠链上频率判断。

### 当前解决

系统采用三层证据模型：

```text
链上事实：transaction / receipt / log / trace
    -> 协议解释：Swap / Wrap / Bridge
    -> 派生结论：画像 / 标签 / 风险关联
```

交易分析只在交易成功时解析 Receipt。Uniswap V3 Swap 除事件 Topic 外，还通过 Pool 的 `factory()` 验证官方 Factory，并读取 `token0`、`token1` 和 `fee`。WETH Wrap/Unwrap 必须来自官方 WETH 合约事件。

Trace 对入选合约关系按单笔金额降序扫描最多 20 笔：

- 只接受成功、完整、无歧义的 Swap/Wrap 证据；
- 转换后按输出 Token 和输出对手方重新累计；
- 未确认转换时终止该合约分支，不根据调用参数或普通 Transfer 猜测；
- 超过扫描上限时返回 `conversionStatus=partial` 和实际扫描数。

跨链只接受已注册的 Ethereum/Base 官方 OP Stack Bridge 证据。源链和目标链通过消息哈希、事件和协议状态关联；无法唯一对应时标记为待定或歧义，不用金额相等和时间接近代替协议证据。

### 仍有边界

当前交易解释集中在 Ethereum 的 Uniswap V3、WETH 和有限官方合约；桥只覆盖 Ethereum/Base 官方 OP Stack 路径。Uniswap V2、1inch、其他聚合器、借贷、质押、Mixer、第三方桥和更多链都需要独立 Adapter，不能用一个通用事件猜测器覆盖。

## 6. 账户制资金归因

### 难点

Ethereum 地址余额是可替代的。地址收到 10 ETH 后再转出 10 ETH，只能证明交易发生在先后两个时间点，不能证明转出的就是先前收到的那 10 ETH。

### 当前解决

当前图使用“资金关系”而非“逐币流向”表述。路径保存地址、方向、资产和代表交易证据，避免将地址关系误写成 UTXO 式资金继承。

对于未来的交易锚点模式，合理约束是：上游区块沿路径单调不增，下游区块沿路径单调不减，并以每一跳的边作为下一跳时间边界。

### 仍有边界

交易锚点和时间有向路径尚未落地。即使实现，它也只能输出“时间一致的资金关联路径”，不能解决账户制资产混同带来的确定归因问题。

## 7. 标签、画像与实体归属

### 难点

高交易量可能来自交易所热钱包，也可能来自 Router、桥、批处理合约、空投或机器人。把高频直接标记为热钱包，会将结构特征误当成实体身份，并在风险传播中放大误报。

### 当前解决

系统区分三类节点信息：

| 类型 | 示例 | 可信含义 |
| --- | --- | --- |
| 结构事实 | 合约账户、`high_volume_hub` | 可计算的工程属性 |
| 行为推断 | `suspected_hot_wallet` | 版本化启发式结论 |
| 确定性标签 | `exchange_hot_wallet`、`hacker`、官方协议 | 人工或可信公开证据 |

`hot-wallet-v1` 使用 30 天窗口的交易数、独立对手方、活跃天数、归集和分发特征生成快照，缓存键包含 `(chain,address,ruleVersion,dataThroughBlock)`。

标签支持从页面节点详情写入，也支持独立管理入口。人工和公开名单标签保留来源、置信度、说明和证据，行为标签不会自动成为风险传播源。

### 仍有边界

`hot-wallet-v1` 没有完整整合账户类型、样本覆盖率和标注数据校准。当前画像按请求计算，没有持久化 `profile_job`、脏地址增量更新和规则升级回填。链上关系也不能证明多个地址由同一实体控制。

## 8. 有界风险传播

### 难点

若风险传播直接复用展示图 TopN，会漏掉小额、多次或最近发生的风险关系；若对新标签执行无界全图 BFS，又会出现扇出、环路、路径组合爆炸和不可控资源消耗。

传播语义也容易被误解：已知攻击地址的邻居只能被描述为“存在关联风险”，不能继承 `hacker` 身份。

### 当前解决

`propagation-v3` 是 Trace 完成后自动创建、以查询目标为中心的持久化任务。它从目标同时向入账和出账方向最多展开 3 跳，仅使用已同步事实，并为每个风险源保留最佳结构化证据路径：

```text
累计金额 Top20
  + 交易次数 Top20
  + 最近交易 Top20
  + 已知风险对手方
  + 用户指定对手方
```

候选地址规范化并去重，每节点最多 50 个；已知风险和用户指定地址优先纳入。查询仍使用按对手方排序的流式游标，三个固定大小堆分别维护金额、次数和最近候选，同时计算：

```text
selectedCounterparties / totalCounterparties
selectedAmount / totalAmount / amountCoverage
truncated / truncationReason
```

传播边界为：

| 参数 | 默认值 |
| --- | ---: |
| `maxHops` | 6 |
| `minExpandConfidence` | 0.15 |
| `strongOutputThreshold` | 0.50 |
| `weakOutputThreshold` | 0.20 |
| `perNodeCandidateCap` | 50 |
| `maxNodes` | 10,000 |
| `maxEdges` | 50,000 |
| `maxPathsPerTarget` | 3 |

路径内出现重复地址时保留闭环证据但不再入队。引擎按 `(sourceLabel,chain,address,direction,asset)` 保存最高置信状态，环路和重复路径不重复加分。到达 `exchange`、`exchange_hot_wallet`、`hot_wallet` 等确定性终点后保留证据并停止扩展。

同资产直接传播；只有已确认 Swap 才能跨资产，只有已确认 Bridge 才能跨链。下游按 `0.8^distance`、上游按 `0.6^distance` 衰减，源标签置信度和基础风险分共同决定结果；交易金额不参与评分。

同一目标可以保存最多 3 条独立证据路径，主分取最高可信路径。结果持久化到 `inferred_risk_associations`，绑定源标签、方向、资产、传播版本和数据水位；新任务完成后，不同传播版本或数据水位的旧结果标记过期，不改写确定性标签。

任务通过 MongoDB 原子领取、租约续期、最大重试、Context 取消和幂等键支持中断恢复。目标链缺少统一数据水位时会显式标记 `cross_chain_waterline_unavailable`。

### 仍有边界

- 多通道仍有每节点 50 个候选和任务总预算，不能承诺全图召回；
- 已知风险地址强制通道依赖本地确定性标签的覆盖质量；
- 阈值尚未使用大规模标注集校准，强弱关联不是法律或合规结论；
- 高扇出、拆单、爆发、新地址比例等结构信号尚未由独立 `fanout_analysis_job` 计算；
- 当前跨链后续状态缺少统一目标链数据水位时只能降级完整度。

## 9. 可靠性与结果完整度

### 难点

空结果可能表示没有交易，也可能表示数据未同步、任务被截断或上游失败。若不携带数据状态，使用者无法区分这些情况。

### 当前解决

- 同步、Trace、传播和桥状态均持久化；
- Handler 统一返回错误码和 `retryable` 语义；
- 游标错误、非法金额和 Context 取消向上传递；
- Trace 和传播结果绑定 `ruleVersion`、`propagationVersion` 和 `dataThroughBlock`；
- 候选传播返回覆盖率与截断原因；
- 前端拒绝展示旧版 Trace 或传播结果，提示重新执行。

### 仍有边界

同步与 Trace 的工作队列主要是单进程模型；进程级限流无法协调多个实例。当前也没有完整的审计日志、指标告警、SLO、链重组修复、多源对账和灾难恢复。

## 10. 结论边界

当前可以确认：

- 三类链上资金事实已统一建模并幂等存储；
- 百万行聚合使用流式分组和固定堆，不将全部交易留在内存；
- `trace-v5` 按对手方累计金额生成有界展示图；
- Swap 和 Bridge 只有在协议证据确认后才改变资产或链；
- `propagation-v3` 独立执行目标中心双向有界风险评估并保留路径证据。

当前不能确认：

- Etherscan 数据等于完整的链上执行历史；
- 图中没有出现的边就不存在；
- 高频地址一定属于交易所或热钱包；
- 同额、近时交易代表同一笔资金或一次跨链；
- 与风险源相邻的地址具有相同身份或恶意意图；
- 没有风险结果就表示地址安全。

未完成能力和对应生产方案见 [Demo 边界与生产化](03-Demo边界与生产化.md)。
