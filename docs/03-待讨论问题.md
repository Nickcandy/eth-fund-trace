# 03 · 已确认决策与待补能力

## 结论

在动手写系统之前，需要先固定数据范围和运行方式，再逐步补齐生产化能力。当前已确认：Etherscan API、Ethereum Mainnet、原生 ETH + 内部交易 + ERC-20、本地 Docker MongoDB。数据模型预留 `chain` 字段，但第一阶段只接 `ethereum`。

---

## 一、已确认的基础决策

### 1. 数据源用哪个？

| 选项 | 说明 |
| --- | --- |
| **Etherscan 免费 API（默认）** | 已建好索引，调接口就能拿交易/内部交易/token 转账；限流约 3–5 req/s、10 万次/天 |
| 公共 RPC | 数据全但要自己扫区块，慢，Demo 不划算 |
| BigQuery 公共数据集 | 全量历史、能批量，但要 GCP 账号 |

> **默认建议**：Etherscan API。理由：Demo 要的是「跑通追踪 + 打标」这个闭环，不是「自建数据管道」。（若想展示工程能力，可以在文档里写明「生产环境会换成 ethereum-etl + 自建库」，但代码用 Etherscan 快速跑通。）

Etherscan 只用于读取公开数据；免费 API Key 足够开发阶段使用，代码需要处理限流、分页、重试和缓存。

### 2. 追踪范围：第一阶段追踪哪些资产？

| 选项 | 说明 |
| --- | --- |
| **原生 ETH + 内部交易 + ERC-20** | 覆盖 ETH、合约 ETH 流动和 USDT 等常见代币 |
| NFT（ERC-721/1155） | 资产语义和估值更复杂，后续增加 |
| 跨链 | 难度大，Demo 不建议做 |

> **已确认**：第一阶段加入 ERC-20。跨链和 NFT 暂不纳入。

### 3. 系统要解决什么问题？

系统的核心工作流是：输入一个地址，向上游和下游追踪资金路径；将已知标签和行为规则传播到链路节点；再根据直接暴露、间接暴露、路径距离、金额和标签置信度计算风险结果。它输出的是可解释的分析线索，不是法律或事实上的定罪结论。

## 二、按默认值走即可的（我已在方案里定好）

### 4. 追踪深度几跳？

**默认 3–5 跳**。太浅看不清链路，太深扇出爆炸 + 置信度衰减到没意义。

### 5. 初始标签从哪来？

**默认：内置一批已知地址（交易所热钱包、Tornado Cash 合约、几个公开披露的黑客/钓鱼地址）+ 允许手动加**。理由：公开标签数据集质量参差、还要持续维护，Demo 阶段手动内置几个「确定性高」的标签即可展示打标能力。

### 6. 打标逻辑怎么定？

**已确认：固定规则 + 简单置信度衰减**（见 04 的伪代码），不做机器学习。规则放在版本化配置中，保证同一输入在同一规则版本下得到可复现结果。

### 7. 图存储用什么？

**默认：MongoDB 持久化交易，查询后构建内存邻接表（Go 的 map）**。理由：Mongo 负责数据复用和索引，内存图负责当前请求的追踪计算。

### 8. 用什么语言和基础设施？

**已确认：Go + Echo + MongoDB**。MongoDB 通过 Docker 在本地运行；图遍历可以使用从 Mongo 查询出的内存邻接表，避免一开始引入图数据库。

> 备选：Python + networkx 能更快出原型，但会让「Go 后端工程师」这个身份弱化。建议 Go。

### 9. 运行模式

**第一阶段：按需查询 + 持久化缓存**。输入地址时补齐缺失数据并执行追踪；后续再增加定时同步、新区块监控和风险告警。

### 10. 要不要风险评分？

**默认：做一个极简版**（直接暴露=高、间接暴露按距离降权）。作为加分项，展示你懂「假阳性」这个点。

## 三、还需要补齐的系统能力

1. **数据同步状态**：记录地址、区块范围、最后同步时间和失败原因，支持断点续抓。
2. **数据质量**：处理 Etherscan 分页、重复交易、异常金额、地址大小写和链重组边界。
3. **标签来源管理**：区分人工标签、公开名单和规则推断，记录来源、时间和证据。
4. **风险解释**：每个风险分数必须能展开到触发规则、路径和交易依据。
5. **查询保护**：限制最大深度、扇出和节点数，避免单次请求拖垮服务。
6. **可观测性**：记录请求参数、耗时、外部 API 调用次数和错误。
7. **数据安全**：API Key 放环境变量，Mongo 不暴露到公网，接口限制查询规模。
8. **回归测试**：用固定的脱敏交易图测试 BFS、标签传播、风险评分，不依赖实时链上数据。

## 四、面试官可能追问（提前准备答案）

1. **「你的追踪和 Chainalysis 差在哪？」**
   → 差在**归因数据库的规模与质量**，不是算法。我的是追踪/打标逻辑的干净实现，头部厂商的护城河是几十万实体、十亿地址的标签库 + 人工复核。

2. **「扇出爆炸怎么处理？」**
   → 深度限制 + 每跳 Top-N 金额裁剪 + 把交易所/合约当终点剪枝。

3. **「怎么保证打标准确？会不会冤枉好人？」**
   → 给置信度而非二值；间接暴露≠有问题；标签要有来源/时间/置信度的审计链；最终靠线下证据（KYC/交易所）交叉验证。

4. **「内部交易为什么重要？」**
   → 混币器、DEX、桥都是合约，经它们流动的价值大多表现为内部交易，漏掉就等于漏掉主要流动路径。

5. **「以太坊怎么聚类地址？」**
   → 不能用比特币的找零地址那套；以太坊用入金地址聚类、资金扇出、时间/手续费相关性。（见 01 和 02 的说明）

6. **「混币器（Tornado）怎么破？」**
   → 诚实说：纯污点分析会被混币器打散、产生大量假阳性；实际会配合金额/时间窗口分析、链下情报、以及监控入金/出金两端。Demo 不吹这个能力。
