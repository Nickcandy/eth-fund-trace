# 资金链路追踪设计

## 1. 目标

资金追踪的目标不是生成尽可能大的地址关系图，而是回答两个问题：查询地址的资金从哪里来，以及这些资金最终流向哪里、在哪个证据明确的终点消失。

结果必须保留链上事实、协议解释和推断归因之间的边界。无法确认的链路停止并记录原因，不为了扩大覆盖范围而猜测。

本设计是当前实现契约。资金链路模式直接替换旧的 TopN/BFS，不保留聚合邻居回退。

## 2. 总体策略

```text
查询地址
  -> 建立该地址的完整事实账本
  -> 按区块/交易顺序计算各资产变化
  -> 向前追收入来源、向后追支出去向
  -> 普通 EOA 按资金时间窗口继续
  -> Swap/Wrap 按单笔交易解析并切换资产
  -> 已知终点、跨链桥、未知合约、无法归因或小额资金停止
```

追踪状态必须携带 `chain`、`address`、`asset`、`amount`、方向、进入交易哈希和区块边界。不能只携带地址，否则会把地址的全部历史资金错误地归因给当前链路。

## 3. 地址集合与区块覆盖

地址集合用于保存已经处理过的地址和数据覆盖，不等同于“待扩展邻居列表”。每个地址的三类事实分别记录覆盖范围：

```text
normal:   txlist
internal: txlistinternal
token:    tokentx
```

第一阶段使用一个连续的完整区间表示：

```go
type Address struct {
    NormalSyncedFrom, NormalSyncedTo     int64
    InternalSyncedFrom, InternalSyncedTo int64
    TokenSyncedFrom, TokenSyncedTo       int64
}
```

如果同步中间存在缺口，不能把两个区间压成一个 `start/end` 并宣称完整。后续需要表达缺口时，升级为每类 action 的 `[]BlockRange`；相邻且完整的区间可以合并。

区块范围的作用是增量同步和确认数据水位，不是限制资金追踪的业务深度。仍然必须使用 `safeHead`，并保留 `startBlock/endBlock` 作为外部索引器的查询边界。

### 3.1 同步规则

- 查询中心地址：从配置的起始区块同步到固定截止区块，已有覆盖只补缺口。当前范围为 `21525891..25860787`。
- 追踪中的普通 EOA：只同步本条资金链路需要的时间窗口；上游不晚于进入区块，下游不早于进入区块。
- 三类 action 独立计算和持久化覆盖，不能用 `txlist` 的范围代表 `tokentx` 或 `txlistinternal` 已完成。
- 只有事实写入成功后才能推进覆盖范围。
- 分页、区间拆分、重试和幂等 upsert 继续保留。

## 4. 地址类型与扩展规则

在扩展地址前先判断地址类型和已知角色：

| 地址类型 | 处理方式 |
| --- | --- |
| 普通 EOA | 按资金进入时间窗口同步并继续追踪 |
| 已知交易所、热钱包、混币器、销毁地址或其他终点 | 记录终点，不再扩展 |
| 已知跨链桥合约 | 保留到达事实，作为终点，不做协议分析 |
| 已知 Swap/Wrap 合约 | 只解析关联的进入交易，不同步合约历史 |
| 未知合约 | 记录进入事实，`stopReason=unsupported_contract`，停止 |
| 高频地址 | 保留已取得事实，标记高频并停止外扩 |

合约不应触发 `AddressNotSyncedError`，也不应被加入普通地址的全历史同步队列。

## 5. 合约与协议交易解析

合约扩展以 `entryTxHash` 为锚点。每个交易哈希在同一链上最多解析一次，并缓存 receipt、Transfer logs、WETH 事件、Swap 事件和必要的 internal calls。

### 5.1 Swap、Wrap 和桥终点

- `Wrap/Unwrap`：确认 `ETH <-> WETH` 和数量，切换到输出资产继续。
- `Swap`：必须得到唯一且完整的 `tokenOut`、`amountOut` 和接收地址；否则记录 `ambiguous_conversion` 并停止该分支。
- 已知桥合约：不解析桥协议；保留普通到达事实并设置 `stopReason=cross_chain_bridge`。
- Receipt、logs 或 internal calls 不完整时，不根据 calldata、合约地址或 Token symbol 猜测资产转换。

当前交易解析器支持的协议范围由 [DEX 交易解析设计](08-DEX交易解析设计.md) 定义。

## 6. 资金账本与时间顺序

事实按 `(blockNumber, transactionIndex, logIndex)` 排序；没有可靠交易索引时使用现有稳定字段，并将排序质量标记为部分。

每种资产独立计算：

```text
期末余额 = 期初余额 + 收入 + Mint - 支出 - Burn - Gas
```

资金批次携带剩余数量。普通地址发生多笔收入和支出时，第一版采用 FIFO 归因：较早收入优先匹配较早支出。FIFO 是可重复的推断规则，不是链上确定证明；结果必须标记 `inferred`。

以下情况不得伪装成确定归因：地址已有无法区分的历史余额；多笔输入同时进入同一 Swap，无法唯一确定输出；交易失败、Token 元数据不完整或 internal 事实缺失；资金经过未知合约或高扇出批处理。

## 7. 小额与高频终止

小额判断使用原始最小单位和 Token decimals，禁止使用 `float64`：

| 资产 | 停止条件 |
| --- | --- |
| ETH/WETH | `< 0.01` |
| USDT/USDC/DAI | `< 10` |
| 其他 Token | 没有可靠价格或元数据时停止；不做美元猜测 |

阈值只停止当前资金分支，不删除已经记录的事实。边界值保留，例如 `0.01 ETH` 和 `10 USDT` 不停止。

### 7.1 高频地址

高频保护按一个地址本次任务读取的三类事实总量计算：

```text
txlist + txlistinternal + tokentx >= 200,000
```

达到上限后：停止继续分页和地址外扩；持久化已经成功写入的事实；地址状态标记 `partial`，原因标记 `high_frequency`；保留连接到该地址的资金边，但不自动赋予 `suspected_hot_wallet` 或其他风险身份。

`high_frequency` 是工程保护状态，不是风险结论。未来完整归档可以作为独立低优先级任务运行，不阻塞交互式追踪。

## 8. 结果状态与可审计性

每条资金链路和每个地址都应记录停止原因、证据级别和覆盖范围：

```text
evidence: confirmed | inferred | partial
stopReason: terminal | cross_chain_bridge | small_amount | unsupported_contract |
            ambiguous_conversion | high_frequency | missing_data |
            cycle
```

任务结果至少包含：访问地址集合、每个地址的 action 覆盖、资金边、资产转换证据、剩余金额、未解释金额和数据状态。

余额对账用于发现缺失数据，不作为无限扩展条件：

```text
reconciliation: complete | partial | inconsistent
unexplained[asset] = 期末余额 - 可解释余额
```

## 9. 开发顺序与验收

1. 扩展 `addresses` 覆盖模型，三类 action 独立补缺口；
2. 增加地址类型/终点判断，禁止合约进入全历史同步；
3. 增加以交易哈希为键的 receipt/协议分析缓存；
4. 建立按时间和资产携带剩余金额的资金状态队列；
5. 实现 FIFO 推断、Swap/Wrap 资产切换、桥终止和停止原因；
6. 实现每个 action 5 万条高频终止和余额对账；
7. 用 `trace-v1` 资金链路结果替换旧 TopN/BFS 主路径；不兼容旧聚合结果，需要重新同步并生成追踪任务。

验收必须覆盖：普通转账、内部 ETH、ERC-20、ETH/WETH Wrap、单跳和多跳 Swap、未知合约、已知终点、小额边界、高频地址、缺口补齐、重复同步和余额不一致。

## 10. 非目标

- 不承诺账户模型下的逐币绝对归因；
- 不以 Token symbol 推断合约身份或美元价值；
- 不为了补齐图而全量同步合约、高频地址或跨链目标地址；
- 当前不跨越 Bridge 追踪目标链；跨链关联作为独立后续能力；
- 不把高频状态自动转换为风险标签；
- 不取消区块水位、确认数、分页和幂等写入机制。
