# 架构决策记录

本文记录当前系统采用的关键架构选择。目标是让行为可审计，避免把隐含假设写进代码。

## ADR-001：ERC-20 不建模为“内部交易”

- 决策：`txlistinternal` 只表示 EVM 调用产生的原生资产转账；ERC-20 资金事实来自 `Transfer` 日志。
- 实现：Token 边保存父交易哈希、日志索引和 `mint|burn|transfer` 类型；缺失日志索引时保存稳定的合成负索引和质量标记。
- 限制：同一交易中的 ETH 与 Token 边不自动推导为兑换关系。

## ADR-002：非标准 Token 元数据允许缺失

- 决策：空 `symbol`、`tokenName`、`tokenDecimal` 不导致整页同步失败。
- 实现：原始整数数量仍必须是非负十进制整数；缺失 decimals 时标记元数据不完整。
- 原因：Token 名称和精度是展示元数据，不是资金事件真实性的必要条件。

## ADR-003：治理采用可选服务端 API Key

- 决策：配置 `HTTP_API_KEY` 后，除健康检查外均要求 `Authorization: Bearer`；未配置时适合本地单机运行。
- 实现：请求 ID、超时、Body 上限、恢复、访问日志和单进程 IP 令牌桶统一由 Echo 中间件处理。
- 限制：不实现分布式限流和用户级权限模型。

## ADR-004：首个 L2 选择 Base

- 决策：支持 `ethereum`（chain ID 1）和 `base`（chain ID 8453）。
- 原因：两者均可通过 Etherscan V2 的 `chainid` 参数使用现有采集接口，复用限流、重试和分页逻辑。
- 隔离：地址、边、任务、标签和画像均使用 chain 字段隔离；相同地址字符串不会跨链连边。

## ADR-005：桥接关系必须有明确协议证据

- 决策：自动桥接关系必须命中注册的桥合约和协议消息；待完成记录可以只有源链证据，`completed` 必须同时具备目标链交易和资产事实。
- 原因：仅凭相同地址、金额或时间接近关联会制造高风险误报。
- 实现：官方 OP Stack Bridge Adapter 解析协议事件和消息标识，持久化双链证据和生命周期；不做启发式自动配对。

## ADR-006：TDD 公共边界

测试只覆盖 Etherscan 标准化、链注册表、Store、HTTP 路由、同步/追踪任务管理器和桥接服务等公共接口，不直接测试私有实现函数。

## ADR-007：高频枢纽与热钱包分离

- 决策：`high_volume_hub` 表示数据规模和图结构事实；`suspected_hot_wallet` 表示行为推断；`exchange_hot_wallet` 等确定性归属必须有人工或可信公开证据。
- 原因：交易量无法区分 EOA 热钱包、自动化账户、路由器、桥和批处理合约。
- 后果：达到同步预算可以停止扩展，但不能仅凭预算超限增加风险标签。

## ADR-008：交互式追踪与全历史归档分离

- 决策：生产环境应默认采用有界、最近优先的交互式追踪；全历史同步作为显式后台归档模式。
- 原因：真实运行中单个高频邻居产生约 87 万事实边并长期阻塞 TraceJob，而 BFS 尚未进入后续层级。
- 状态：尚未实现；当前代码仍要求待展开地址完成全历史同步。

## ADR-009：交易锚点使用时间有向路径

- 决策：按 txHash 追踪时，上游路径区块单调不增，下游单调不减；每跳以当前边作为下一跳时间边界。
- 原因：仅把锚点区块传为 `startBlock` 会丢失上游，并混入时间上不可能由锚点资金触发的边。
- 限制：账户模型中的余额可替代，时间一致路径仍不是逐币归因证明。

## ADR-010：L2 链内事实与桥接关联分层

- 决策：L2 链内事实继续使用独立链域的统一 Transfer 模型；跨链桥接使用独立关系和双端证据。
- 原因：Base 存款、提款和跨域消息具有不同生命周期，不能建模为一条普通同链转账。

## ADR-011：DEX Swap 属于可验证解释层

- 决策：`Transfer` 继续保存资金事实，`SwapEvent` 保存协议解释，两者通过 `chain + txHash` 关联。
- 验证：Universal Router 只表示入口；只有 Swap 日志 emitter 的 `factory()` 等于官方 Uniswap V3 Factory 才认定为 Uniswap V3 Pool。
- 行为：多个 Swap 按日志顺序展示；不能唯一确定总体输入输出时标记 `ambiguousRoute`，不猜测单一路线。
- 限制：从 Swap 输出地址继续的现有 TraceJob 是地址级关联分析，不是逐币归因证明。

## ADR-012：官方桥识别复用跨链图边

- 决策：仅对注册的 Ethereum↔Base 官方 OP Stack Bridge 自动识别 ETH/ERC-20，并复用 `cross_chain_links` 保存生命周期状态。
- 证据：以桥合约事件、跨域消息哈希/nonce、两端确认交易和 Transfer 事实作为配对依据；不根据相同地址、金额或时间接近推断。
- 状态：提款允许 `initiated/proven/finalized/completed`，目标执行事实缺失时不标记为已到账；证据冲突标记 `ambiguous`。
- 限制：状态刷新使用有界后台轮询，不绑定 HTTP 请求；不修改地址追踪模型，也不宣称逐币归因。

## ADR-013：资金链路追踪替代地址广度优先扩展

- 决策：以带时间、资产和剩余金额的资金状态队列作为 `trace-v1` 主追踪模型；Trace 不保留 `TopN/BFS` 兼容回退。
- 原因：地址邻居数量不能代表资金链路，账户余额混合后也不能把地址全部流水归因给查询资金。
- 约束：中心地址建立完整事实账本，链路 EOA 按进入交易的时间窗口同步；合约按单笔进入交易解析，不进入全历史同步。

## ADR-014：地址按 action 独立记录区块覆盖

- 决策：`txlist`、`txlistinternal` 和 `tokentx` 分别记录已完成区块范围，并只补各自缺口。
- 原因：三类索引数据的完整性不同，一个地址级 `start/end` 无法证明所有事实类型都已覆盖。
- 约束：区块水位和 `safeHead` 仍用于增量同步与重组保护；存在缺口时不得宣称完整。

## ADR-015：合约只做锚点交易解析

- 决策：已知 Swap/Wrap/Bridge 合约只解析资金进入的 `entryTxHash`；未知合约停止扩展并记录 `unsupported_contract`。
- 原因：合约历史通常高扇出，全量同步会把交互式追踪退化成地址归档。
- 约束：Swap 只有唯一且完整的输出资产、数量和接收地址才可继续；不根据 calldata、symbol 或相近金额猜测。

## ADR-016：高频地址和小额资金是显式终点

- 决策：单地址本次读取的 `txlist + txlistinternal + tokentx` 达到 200,000 条时停止分页和外扩，标记 `partial/high_frequency`；`ETH/WETH < 0.01`、`USDT/USDC/DAI < 10` 的资金分支停止。
- 原因：高频地址和低价值分支的继续扩展成本高，且不能提升可解释性。
- 约束：高频是工程保护状态，不是风险标签；阈值比较使用最小单位和 `big.Int`，不使用 `float64`。

## ADR-017：跨链桥暂作为资金追踪终点

- 决策：下一阶段链内资金追踪遇到跨链桥合约或已识别的桥协议交易时，记录源端事实和协议证据，并以 `cross_chain_bridge` 终止；不查询目标链，不等待目标交易完成。
- 原因：跨链消息和目标链执行具有独立生命周期，当前优先保证单链资金归因的时间和金额边界，避免桥接关联重新引入跨链图的范围爆炸。
- 约束：现有 `bridge` 模块仍可独立分析和刷新桥证据；该能力不自动改变资金追踪路径。未来跨链追踪必须作为独立模式定义两端水位、消息证据和重组处理。
