# M12 官方桥识别与状态同步设计

## 1. 目标与边界

M12 为 Ethereum Mainnet 与 Base 之间的官方 OP Stack Bridge 增加自动识别和状态同步能力。用户提供任一侧的交易哈希或地址后，系统从已采集的链上事实中识别 ETH/ERC-20 存款、提款和对应的跨域消息，并复用现有 `cross_chain_links` 作为图上的跨链边。

本轮支持：

- Ethereum ↔ Base；
- 原生 ETH；
- 通过官方 Standard Bridge 支持的 ERC-20；
- 存款（Ethereum → Base）和提款（Base → Ethereum）；
- 基于事件、消息哈希和目标链确认事实的状态同步。

本轮不支持：

- 第三方桥、跨链聚合器和交易所内部转账；
- 仅凭相同地址、金额或时间接近进行配对；
- 自动跨链资产价格换算或逐币资金归因；
- 修改现有地址、Transfer、TraceJob 或 BFS 追踪模型。

## 2. 协议注册表

桥地址必须按链 ID 和网络版本配置，不能只按地址字符串识别。注册表使用官方部署资料作为来源，并在代码中保留版本和来源 URL。

| 角色 | Ethereum | Base | 用途 |
| --- | --- | --- | --- |
| L1 标准桥 | `L1StandardBridge` | - | Ethereum 存款锁定/释放、ERC-20 事件 |
| L2 标准桥 | - | `L2StandardBridge` | Base 铸造/销毁、ERC-20 事件 |
| L1 门户 | `OptimismPortal` | - | Base 提款最终化和消息执行 |
| L2 消息发送器 | - | `L2ToL1MessagePasser` | Base 提款消息承诺 |

实际地址以注册表版本为准；未命中注册表的合约只能保留普通交易/Transfer 事实，不得标记为官方桥。

ETH 与 ERC-20 使用不同的事件适配器。ERC-20 适配器必须同时验证 Token 合约、桥合约和 `from/to/value` 关系，避免把桥合约内其他 Transfer 误识别为桥接资产。

## 3. 链上证据语义

### 3.1 Ethereum → Base 存款

存款的源端证据是 Ethereum 上 Standard Bridge 的 ETH 存款或 ERC-20 `Deposit` 事件，通常包含发送者、接收者、Token、金额和目标链语义。目标端证据是 Base 上对应 Token/ETH 到达接收地址的铸造或释放事实。

识别要求：

1. 源交易已确认且 Receipt 成功；
2. 日志 emitter 是注册的官方桥或经注册的 L1 Token Bridge；
3. 源资产、金额、源地址和目标地址可从事件字段确定；
4. Base 目标事实存在，或有明确的跨域消息标识可继续等待目标事实；
5. 配对键优先使用官方消息哈希，其次使用协议定义的 nonce/事件关联，禁止仅靠启发式匹配。

### 3.2 Base → Ethereum 提款

提款分为发起、证明、最终化、执行多个阶段。Base 源端通常产生 `L2ToL1MessagePasser` 消息承诺和 Standard Bridge 销毁/提款事实；Ethereum 目标端在证明和最终化后产生 Portal/Standard Bridge 执行事实。

没有 Ethereum 目标执行交易时，仍可建立状态为 `initiated` 或 `proven` 的待完成边，但不得把它标记为 `confirmed`，也不得在图上伪造已到账的目标事实。

## 4. CrossChainLink 扩展

继续使用现有 `cross_chain_links` 集合和唯一证据索引。为兼容已存在的人工确认记录，新增字段均可选：

```text
protocol        official_opstack_bridge
direction       deposit | withdrawal
messageHash     协议消息哈希，可为空
nonce           协议 nonce，可为空
sourceBlock     源链区块
targetBlock     目标链区块，可为空
status          initiated | proven | finalized | completed | failed | ambiguous
evidenceLevel   confirmed | strong | partial
lastCheckedAt   最近状态检查时间
nextCheckAt     下次检查时间
adapterVersion  bridge-opstack-v1
```

现有字段 `sourceTxHash/sourceLogIndex/targetTxHash/targetLogIndex` 继续保存两端事实。`targetTxHash` 为空表示目标事实尚未出现；`status=completed` 必须同时存在目标交易和目标 Transfer 证据。`Status=confirmed` 的历史人工记录不强制迁移，但新适配器统一使用上述生命周期状态和 `evidenceLevel`。

推荐的自动记录唯一键：

```text
(protocol, sourceChain, sourceTxHash, sourceLogIndex, targetChain, messageHash)
```

若 `messageHash` 缺失，则使用源端事件证据键，后续发现消息哈希时通过幂等更新补全，不创建第二条边。

## 5. 状态机

```text
initiated -> proven -> finalized -> completed
    |           |          |
    +---------> failed <---+

任意状态 --证据冲突/无法唯一配对--> ambiguous
```

- `initiated`：源端桥事件已确认，目标消息或目标事实尚未确认；
- `proven`：提款证明或等价协议步骤已确认；存款通常跳过此状态；
- `finalized`：跨域消息已满足协议最终化条件；
- `completed`：目标链执行交易和目标资产事实均已确认；
- `failed`：源交易失败、消息被协议明确拒绝，或超过保留期后确认不可完成；
- `ambiguous`：存在多个候选目标事实、事件解析不完整或协议证据冲突。

状态只能沿协议允许的方向前进，重复轮询不得回退已确认状态。目标链重组风险由确认数配置控制；在达到确认数前只保存观察结果，不推进为最终状态。

## 6. 处理流程

1. 从交易 Receipt、Transfer 和已知桥合约日志中提取候选源事实；
2. 通过消息哈希/nonce 查询另一侧链的消息和桥事件；
3. 对候选目标事实执行地址、资产、金额、链 ID 和消息关联校验；
4. 使用唯一键 upsert `cross_chain_links`，保存证据来源和解析版本；
5. 对 `initiated/proven/finalized` 记录安排受限的后台检查；
6. 发现目标执行后更新同一条边为 `completed`，使现有 fund graph 自动显示跨链边；
7. 上游限流、RPC 超时或证据暂缺时保留当前状态，并记录 `lastCheckedAt/nextCheckAt`，不把暂缺当失败。

状态同步必须是有界任务：每次最多检查固定数量的链接和消息，每条链接有重试上限和退避时间。同步器使用现有 Etherscan/RPC 共享限流，API Key 不进入日志。

## 7. API 与前端契约

M12 优先扩展现有查询，不改变现有地址追踪接口：

- `GET /api/v1/bridge-links` 增加 `status`、`protocol`、`direction` 过滤；
- `POST /api/v1/bridge-links` 保留人工/公开证据写入兼容性；自动适配器写入同一集合；
- 可选新增 `POST /api/v1/bridge-sync` 触发有界状态刷新，返回异步任务 ID。

前端沿用现有虚线跨链边，增加协议、方向、资产、金额、当前状态和证据等级。`initiated/proven/finalized` 显示为“待完成”状态，不渲染成已到账；`ambiguous` 显示候选证据和原因，不自动进入风险结论。

## 8. 错误与数据质量

可识别错误包括：

- `bridge_unknown_contract`：emitter 不在官方注册表；
- `bridge_malformed_event`：必需字段无法解析；
- `bridge_ambiguous_match`：多个目标候选无法唯一确定；
- `bridge_upstream_rate_limited`：上游限流；
- `bridge_upstream_unavailable`：上游不可用或超时。

前两类是事实解析问题，后两类是可重试的同步问题。所有错误保留在链接的质量字段或任务日志中，不能吞咽，也不能将暂时不可用写成 `failed`。

## 9. 验证计划

- 固定 Receipt fixtures：ETH 存款、ERC-20 存款、ETH 提款各生命周期、失败交易、伪造桥事件和多候选目标；
- 单元测试：topic/ABI 解码、注册表匹配、消息键、金额字符串、状态单调推进和幂等 upsert；
- Mongo 集成测试：同一源事件重复扫描只产生一条 `cross_chain_link`，状态刷新不产生重复边；
- HTTP 测试：状态/协议/方向过滤、待完成响应和上游错误 envelope；
- 外部 live 测试仅在显式配置 API Key 和开关时运行；普通测试不访问网络；
- 前端测试：跨链边状态展示、待完成与歧义降级、刷新后状态恢复。

验收标准：对固定的 Ethereum↔Base 官方桥样本，系统能识别 ETH/ERC-20、保留两端交易证据、幂等更新同一条图边，并在目标链事实出现后将状态推进到 `completed`；未知桥合约不会被误识别。

## 10. 依赖与风险

- 官方桥部署地址、事件 ABI 和消息生命周期必须版本化；升级时新增注册表版本，不覆盖旧证据；
- Etherscan 地址历史接口不保证提供完整跨域消息语义，必要的消息状态读取需要 Proxy/RPC 适配；
- Base 提款最终化可能跨越较长时间，必须采用后台轮询和退避，不能绑定 HTTP 请求生命周期；
- 目标链事件可能因重组变化，完成状态必须有确认数和可重复校验；
- 资金图仍表达“有协议证据的跨链关系”，不宣称逐笔资产归因。
