# 运行难点与工程结论

## 1. 真实运行事件

2026-08-23 的一次 `depth=3, topN=10, direction=both` 地址追踪暴露了当前同步策略的主要瓶颈。

种子地址只产生 16 条记录，并很快同步完成。BFS 遇到第一层未同步邻居 `0xd152...2150` 后，追踪进入 `waiting_sync`，开始同步该邻居的全部历史。

一次观测快照如下：

| 指标 | 数值 |
| --- | ---: |
| Mongo 唯一事实边 | 约 87 万 |
| Etherscan 累计读取 | 约 88 万 |
| API 页面 | 约 8800 |
| 区块范围拆分 | 约 87 次 |
| 已同步完成地址 | 1 |
| 正在同步地址 | 1 |

结论：数据量并不是“100 个节点各 1 万条”产生的，几乎全部来自一个高频邻居。10,000 是单个 action/区间分页窗口上限，不是单地址总量上限；同步器会继续拆分区块范围，因此单地址可以产生数十万条事实边。

## 2. 热钱包问题

### 2.1 不能用交易量直接判定热钱包

高交易量可能来自：

- 交易所热钱包；
- 归集或支付钱包；
- 机器人 EOA；
- DEX Router、桥、批处理器等合约；
- 空投、垃圾 Token 或系统性调用。

因此应拆分三个概念：

| 概念 | 含义 | 是否确定性 |
| --- | --- | --- |
| `high_volume_hub` | 达到工程预算的高频图枢纽 | 是数据规模事实 |
| `suspected_hot_wallet` | 满足行为规则的疑似热钱包 | 否，属于推断 |
| `exchange_hot_wallet` | 有人工或可信公开证据的交易所热钱包 | 是确定性标签 |

`high_volume_hub` 应用于同步截断和 BFS 剪枝，但不能自动写成 `hot_wallet`。

### 2.2 当前 `hot-wallet-v1` 的局限

- 依赖地址同步完成后才计算，无法及时处理高频地址；
- 没有先区分 EOA 与合约；
- 30 天窗口基于已入库数据，截断样本目前没有完整度字段；
- 事件数量反映活动强度，不等于地址归属；
- 同一控制主体可能轮换多个地址，单地址画像无法完成实体识别。

### 2.3 推荐结论

先做账户类型与有界画像，再决定行为分类：

```text
账户类型 -> 样本完整度 -> 双向活动 -> 对手方/活跃天数
         -> 归集/分发模式 -> suspected_hot_wallet
```

合约默认进入基础设施分类，不参与 EOA 热钱包规则；人工证据仍可覆盖为确定性标签。

## 3. 单节点交易过多

### 3.1 当前原因

当前交互式 BFS 要求待展开地址先完成全历史同步。每个地址依次查询：

```text
txlist -> txlistinternal -> tokentx
```

客户端默认每页 100 条、每个范围最多 100 页。达到上限后以原始最后记录区块为边界续跑，并对 Mongo 幂等 upsert。这个机制保证不静默漏数据，但不限制一个地址的总成本。

### 3.2 工程影响

- 单个高频节点阻塞整个 TraceJob；
- 按项目当前 5 QPS limiter，8800 页理论请求时间下限约 29 分钟；按官方 Free 3 QPS，理论下限约 49 分钟。实际还包括重试、Mongo 写入和边界重读；
- BFS 深度尚未展开，数据库已经写入大量与当前 Top-N 无关的事实；
- 全历史同步、交互式追踪和归档三个目标被耦合在一条路径中。

### 3.3 推荐处理

交互式地址追踪采用共享预算：页面数、记录数、耗时、同步地址数和任务总调用数任一超限即停止。保存已确认事实，状态为 `partial/truncated`，并将该节点标为 `high_volume_hub` 和遍历终点。

完整历史同步独立为后台归档任务，不再作为每次分析的前置条件。

## 4. 内部交易问题

“内部交易”不是独立的链上交易对象，而是交易执行期间产生的调用轨迹和原生资产 value 转移。工程难点包括：

- 与父交易共享 `txHash`，必须使用 `traceId` 等路径标识去重；
- 失败或回滚调用不能作为最终资金事实；
- 不同数据源对 trace 深度、错误和排序表达不同；
- 普通归档节点不一定开放历史 tracing；
- 一个高频合约可能产生远多于顶层交易数量的内部记录。

当前系统使用 Etherscan `txlistinternal`，适合 Demo，但不能宣称等价于完整执行追踪。

## 5. ERC-20 问题

ERC-20 转账不是“ERC-20 内部交易”。它是合约日志中的 `Transfer` 事件，与内部 ETH value 转移属于不同事实来源。

主要难点：

- Token 合约、发送方、接收方和原始整数共同决定资金事实；
- decimals/symbol/name 是展示元数据，可能缺失或异常；
- mint/burn 使用零地址端点；
- Etherscan 响应可能缺少真实 `logIndex`，当前使用稳定负数合成索引并标记质量；
- 非标准 Token、代理合约和伪造元数据会影响展示可信度；
- 同一交易同时出现 ETH 与 Token，并不能仅凭同哈希推导为兑换。

金额始终保留字符串，不跨 Token 或 ETH 相加。

## 6. Layer 2 与跨链问题

L2 应拆成两个问题。

### 6.1 链内数据

Base 等 EVM L2 可以复用地址、交易和 Token 模型，但必须使用 `(chainId,address)` 隔离身份。确认数、最终性、数据可用性和数据源覆盖范围不能直接照搬 Ethereum。

### 6.2 跨链关联

桥接不是一条普通跨链转账。源链锁定/销毁和目标链释放/铸造是两组链上事实，需要桥协议的消息 ID、事件或其他可靠证据关联。

当前项目只接受同时提供源链和目标链交易证据的 `cross_chain_link`，不根据相同地址、相近金额或时间自动推断。这降低覆盖率，但避免制造错误路径。

## 7. 其他复杂问题

### 7.1 图扇出

单向 `depth=3, topN=10` 理论节点上限为 `1+10+100+1000=1111`。双向分别取入/出候选，增长更快，当前以 5000 节点硬上限保护。地址去重和终点剪枝会降低实际数量。

### 7.2 Top-N 的可比性

不同 Token 和 ETH 没有统一金额单位。当前根节点包含 ETH 与链级官方 ERC-20 白名单，并在每种资产内按累计整数金额排序；只有经过验证的合约兑换才切换资产，仍不进行跨资产金额比较。

### 7.3 数据完整度

空结果可能意味着确实无交易、上游不覆盖、查询窗口截断或同步失败。每个结果都应携带覆盖区块、数据状态、截断原因和规则版本。

### 7.4 异步任务

任务保存在 Mongo，但 worker 和活动任务锁在进程内。服务重启会将遗留任务标记 `interrupted`，不会自动恢复。前端必须保存 job ID；当前已通过 URL 恢复 TraceJob。

### 7.5 标签传播和假阳性

与高风险地址存在路径不等于控制关系或违法事实。传播必须显示来源、方向、距离、置信度、路径和交易哈希，并设置最低阈值。

### 7.6 外部 API 和成本

当前限流只保证单进程共享配置值 5 QPS，不管理多实例配额、每日调用量或第三方服务故障。官方当前 Free 为 3 QPS、Lite 为 5 QPS，因此实际部署必须按 Key 套餐配置。生产化还需要集中限流、任务预算、调用计费指标和替代数据源。

## 8. Demo 应如何表达

可以展示：

- 三类事实边被统一建模；
- 异步同步和分页进度可观察；
- BFS、标签传播、风险规则和图展示形成闭环；
- 真实运行发现高频节点会让全历史策略失效；
- 下一阶段通过有界追踪和交易锚点解决。

不能宣称：

- 交易多就一定是热钱包；
- Etherscan 数据等于完整链上执行历史；
- 相同地址或相近金额足以证明跨链桥接；
- 没有风险结果就代表地址安全；
- 当前 Demo 已经适合无限深度或大规模生产查询。
