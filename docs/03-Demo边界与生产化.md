# Demo 边界与生产化

## 1. 文档目的

本文只回答四个问题：当前已经完成什么、哪些 Feature 尚未完成、哪些能力为控制 Demo 范围而主动删减，以及升级为生产级系统时应如何建设。

状态定义：

- **已实现**：当前代码、接口和测试已经存在；
- **未完成**：产品上有价值，但当前代码没有形成完整闭环；
- **Demo 删减**：为控制数据、协议和运维复杂度而主动限制，不应被理解为生产方案；
- **生产要求**：上线前需要补齐的工程能力，不代表已经实现。

## 2. 当前已实现

### 数据与查询

- Ethereum/Base 的普通 ETH、内部 ETH、ERC-20 地址历史采集；
- 分页、重试、检查点、区间拆分、安全链头和批量幂等写入；
- MongoDB 方向/资产复合索引和稳定游标分页；
- 对手方累计金额 TopN，流式分组和固定大小堆；
- 地址、同步任务、TraceJob、标签、画像、传播任务和协议证据持久化。

### 分析能力

- `trace-v5` 上下游分层资金图；
- 官方 Token 白名单和确定性 Token 元数据；
- Ethereum Transaction/Receipt、ERC-20 Transfer、WETH 和 Uniswap V3 解释；
- Ethereum/Base 官方 OP Stack Bridge 的有限协议解析和生命周期；
- `hot-wallet-v1` 地址画像；
- 人工/公开确定性标签；
- `propagation-v3` 目标中心双向最多 3 跳风险评估和 `risk-association-v2` 评分；
- 节点、边、证据路径、覆盖率、截断原因和任务状态的前端展示。

这些能力构成了从外部数据采集、事实存储、查询聚合到解释输出的 Demo 闭环。

## 3. 未完成 Feature

| Feature | 当前缺口 | 生产实现方式 |
| --- | --- | --- |
| 有界地址追踪 | Trace 遇到未同步邻居时仍可能等待全历史同步 | 增加 `bounded_address` 覆盖模式及页数、记录数、时间、地址数和写入量预算；超限返回 `partial/truncated` |
| 交易锚点追踪 | 可分析单笔交易，但不能从该交易按时间因果展开上下游 | 增加 `anchored_transaction`，路径上游区块单调不增、下游单调不减，并显示归因限制 |
| 完整归档模式 | 当前同步策略与交互追踪耦合 | 独立 `archive_address` 后台队列，使用低优先级、独立配额和可恢复检查点 |
| 地址当前余额 | 当前只展示历史流量，不能回答地址此刻持有多少 ETH/Token | 在明确区块读取 `eth_getBalance` 和白名单 Token `balanceOf`，返回查询区块、RPC 来源和 Token decimals；不从流入减流出推算余额 |
| `fanout_analysis_job` | 风险传播有多通道候选，但未计算拆单、爆发和低集中度行为信号 | 在固定时间窗聚合收款方数量、熵、集中度、新地址比例和 burst，任务化执行并保留样本覆盖率 |
| `profile_job` / `hot-wallet-v2` | 画像按请求计算，规则未使用完整账户类型与样本覆盖 | 由同步完成事件标记 dirty，持久化任务原子领取；维护增量特征并使用标注数据校准规则 |
| 标签生命周期 | 可以写入和查询标签，但缺少完整撤销、审批和外部名单同步 | 增加版本、有效期、审批人、来源签名、撤销记录和定期名单同步；撤销后使派生关联过期 |
| 实体聚类 | 地址之间只有关系，没有主体归属模型 | 建立独立 Entity/Address Membership 模型，只输出带特征和置信度的候选聚类，人工确认后才成为确定关系 |
| 通用 DEX/协议解析 | 主要覆盖 Uniswap V3 与 WETH | 按协议和版本建立 Adapter Registry、合约注册表、ABI 版本、固定交易样本和降级策略 |
| 生产级跨链索引 | 只支持有限官方桥按需分析和状态同步 | 分链增量索引桥事件，以 message hash/nonce 关联，保存双链水位并处理重组、补块和协议升级 |
| 多链支持 | 当前链注册表仅覆盖 Ethereum/Base 的既定语义 | 每条链单独配置最终性、RPC、Token 注册表、Trace 来源和协议 Adapter；禁止只复制 Chain ID |
| 价格与组合价值 | 金额按原始资产展示，不能跨资产比较 | 使用带时间戳和来源的价格快照，在查询层派生估值；原始最小单位金额始终保留，不用价格覆盖事实 |
| 实时告警与案件工作流 | 当前以交互查询为主 | 将已确认标签和规则结果接入可重放事件流，提供订阅、告警去重、调查 Case、处置状态和审计记录 |

## 4. Demo 主动删减

### 4.1 数据范围

Demo 采用“查询地址后按需同步”，没有持续索引全链。这样可以用有限 API Key 验证完整链路，但代价是首次查询延迟、邻居数据缺失和高频地址同步阻塞。

Demo 依赖 Etherscan 地址历史，没有自建全链 Transaction、Receipt、Log 和 Trace 索引。标准 JSON-RPC 本身不提供任意地址的完整历史，因此生产环境不能简单地把 Etherscan 调用替换为一个 RPC 请求。

### 4.2 任务调度

同步和 Trace 使用单进程有界队列，任务结果写 MongoDB；它满足本地取消和状态展示，但不保证多实例唯一消费和自动接管。

风险传播已经使用 MongoDB 租约、续租和重试，这是生产任务模型的局部实现，但还没有优先级、租户配额、死信队列、人工重放和跨任务资源预算。

### 4.3 聚合存储

Demo 没有为所有地址预计算 TopK。TopK 的真实维度包含链、方向、资产、时间窗、K、数据水位和覆盖模式，盲目物化会导致写放大和失效复杂度。

当前流式查询内存有界，但高频地址查询耗时仍与匹配记录数相关。只有压测证明在线扫描成为瓶颈后，生产环境才应增加增量聚合桶或热点物化视图。

### 4.4 协议和资产

Demo 使用固定官方 Token 和协议合约白名单，避免非标准 Token 元数据、代理升级和伪造事件被误解释。它没有尝试支持任意 Token、任意 Router 或任意 Bridge。

### 4.5 风险结论

Demo 不自动把传播结果写成目标地址标签，不按金额提高风险分，也不把 `suspected_hot_wallet` 作为传播源。这些限制是为了保持“事实、协议解释、行为推断、实体身份”之间的边界。

## 5. 生产级参考架构

```text
                       调查控制台 / API Client
                                  |
                       API Gateway / Auth / RBAC
                                  |
                 +----------------+----------------+
                 |                                 |
          Query Service                      Job Service
     图/事实/画像/风险读取             创建/取消/进度/配额
                 |                                 |
       +---------+---------+             Durable Queue / Lease
       |                   |                       |
  Mongo 元数据与任务   聚合/分析存储       Worker Pools by workload
       |                   |                       |
       +---------+---------+-----------------------+
                 |
        Canonical Fact Processing
                 |
       +---------+----------+
       |                    |
 地址历史 Indexer     RPC Block/Receipt/Log/Trace
       |                    |
       +---------+----------+
                 |
      Ethereum / Base / More Chains

Raw payload -> Object Storage（回放、审计、重建）
All services -> Metrics / Logs / Traces / Alerts
```

生产系统应把“采集平面、计算平面、查询平面”分开。用户查询不能直接触发不可控的全历史工作；归档、回填、画像、传播和专项分析使用不同队列、优先级和资源池。

## 6. 生产建设要求

### 6.1 数据采集与一致性

- 为每条链保存区块号、区块哈希和父哈希，检测 canonical chain 变化；
- 使用 safe/finalized 策略，并保留可重扫重叠窗口；
- 重组时撤销旧区块事实，重放受影响 Transfer、协议解释、聚合和风险结果；
- 原始上游响应进入低成本对象存储，支持审计和解析器升级后重放；
- 为地址索引、RPC、Trace 和价格数据配置主备来源，记录来源和采集时间；
- 建立缺块、缺页、重复率和跨来源对账任务；
- 全链规模若超出 MongoDB 的经济边界，原始分析事实进入分区列式存储，MongoDB 保留任务、标签、证据和在线查询视图。

对于仅服务有限调查地址的产品，MongoDB 可以继续作为主事实库，但必须按链和访问模式分片，并通过真实容量测试确定分片键、热分区和索引成本。

### 6.2 覆盖模式与预算

所有同步和分析请求必须显式选择覆盖模式：

| 模式 | 用途 | 必须返回的状态 |
| --- | --- | --- |
| `bounded_address` | 低延迟交互调查 | 时间窗、页数/记录预算、覆盖率和截断原因 |
| `anchored_transaction` | 围绕交易分析前后关联 | 锚点区块、路径时间约束和证据质量 |
| `archive_address` | 完整历史归档 | 检查点、数据源、水位、失败分片和完成状态 |

预算至少覆盖 API 页数、外部请求数、扫描记录、MongoDB 写入、节点、边、运行时间和估算成本。预算耗尽必须产生部分结果，不能伪装成“没有交易”。

### 6.3 持久化任务平台

同步、Trace、画像、传播、桥状态和回填任务应统一具备：

- 可重现的幂等键和输入快照；
- 原子领取、租约、心跳、超时接管和最大尝试次数；
- 优先级、租户配额、并发限制和外部 Provider 配额；
- Context 取消、可重试错误分类、指数退避和死信状态；
- 进度节流、结构化错误码、人工重放和审计日志；
- 输出版本、数据水位、代码/规则版本和失效关系。

可以继续使用 MongoDB 原子领取处理有限规模任务；当吞吐、延迟隔离或事件回放成为瓶颈时，再引入专用消息系统。不要为了“生产化”先增加没有容量依据的基础设施。

### 6.4 查询与聚合

- 保留稳定游标，禁止对百万级结果使用大 `skip`；
- 按 `(chain,address,direction,asset,counterparty,timeBucket)` 增量维护日级或小时级汇总；
- 原始事实是最终可审计来源，聚合可被删除和重建；
- 聚合和缓存键必须包含数据水位、覆盖模式、规则版本和时间窗；
- 仅对实际热点物化 TopK，使用增量桶合并而不是每次重扫全历史；
- 定期执行 `explain("executionStats")` 和高频地址基准，监控扫描/返回比、磁盘排序、P95/P99 和堆内存。

高扇出检测不应无限扩大交互图。普通查询发现低覆盖率或异常结构后，创建独立 `fanout_analysis_job`，使用更大但仍有限的时间窗和候选预算。

### 6.5 协议与跨链

- 每个协议 Adapter 绑定链、合约地址、部署区块、ABI、代码哈希和版本；
- 协议升级后新旧 Adapter 并存，历史结果保留解析版本；
- 使用固定主网交易 Fixture 做回归，未知事件降级为事实而不是猜测；
- 跨链按链维护独立水位，使用协议消息 ID 关联，不用金额和时间模糊匹配；
- Bridge 状态任务按协议最终性和挑战期调度，链不可用时保持 unknown/pending；
- Token 映射需要验证本地/远端合约、decimals 和桥注册表版本。

### 6.6 标签与风险治理

- 确定性标签记录来源、证据、有效期、审批和撤销历史；
- 行为信号、关联风险和实体身份使用不同集合和权限；
- 每个规则版本保存特征定义、阈值、训练/校准样本和上线时间；
- 使用标注集评估召回率、误报率和不同地址类型的偏差；
- 多路径结果取最高可信主分，证据路径独立保留，禁止环路重复加分；
- 标签撤销、规则升级、重组和数据回填触发派生结果失效与重算；
- 高风险输出进入人工复核，不直接触发不可逆处置。

风险分应被解释为在特定数据水位、候选预算和规则版本下的关联强度，而不是事实身份、违法判断或资产冻结依据。

### 6.7 API、安全与审计

- 使用统一身份认证、RBAC、租户隔离和操作审计；
- 写标签、停止任务、重放任务和修改规则需要更高权限；
- Secret 进入专用密钥管理，API Key 不出现在浏览器和日志；
- 响应统一返回 `dataStatus`、`coverageMode`、区块范围、数据源、截断原因和版本；
- 大结果使用异步导出和对象存储，不在在线 API 返回无界 JSON；
- 为公开错误使用稳定错误码，内部错误和上游 Payload 只进入受控日志。

### 6.8 可观测性与容量

生产前需要定义并压测 SLO，而不是沿用 Demo 参数。至少监控：

- 外部 Provider 的成功率、限流率、延迟、剩余额度和每任务成本；
- 各任务队列深度、等待时间、执行时间、重试、租约接管和失败原因；
- MongoDB 扫描/返回比、聚合磁盘使用、慢查询、连接池和副本延迟；
- 每链数据水位、落后区块、缺块、重组深度和跨源差异；
- Trace/传播的节点数、边数、覆盖率和各类截断原因；
- Go 堆、GC、goroutine、文件描述符和进程重启。

日志、指标和 Trace 使用同一请求 ID、任务 ID、链和数据水位关联。告警应对应可执行的处置手册，不能只收集仪表盘。

### 6.9 发布与恢复

- 所有索引和 Schema 变更使用可回滚迁移；
- 新解析器和风险规则先 shadow 运行，对比旧版本结果；
- 定期验证 MongoDB 备份恢复和对象存储原始数据重建；
- 大规模回填使用独立资源池并限速，避免影响在线查询；
- 发布前使用百万级和高扇出 Fixture 执行容量、故障注入和 Context 取消测试。

## 7. 生产验收底线

生产上线不能只以“功能可用”为标准，至少需要证明：

- 任意结果都能说明数据来源、区块范围、完整度、规则版本和证据；
- 上游超时、限流、游标错误、进程重启和任务取消不会静默丢数据；
- 高频地址不会让单个请求占满实例或绕过任务预算；
- 链重组后事实和所有派生结果可以被识别、撤销和重算；
- 多实例不会重复执行同一不可幂等工作，也不会突破共享 Provider 配额；
- 标签撤销和规则升级可以追踪影响范围并使旧风险关联失效；
- 备份可恢复，历史原始数据可重放，关键告警有处置手册。

在这些条件达成前，系统应继续明确标识为有界分析工具，而不是全链、实时、完备的生产风控平台。
