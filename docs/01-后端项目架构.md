# 后端项目架构

## 1. 系统定位

系统是面向 Ethereum 和 Base 的只读资金分析服务。它将地址历史、交易 Receipt、合约调用结果和桥协议事件分层处理，最终输出可回查的资金事实、关系图和风险关联。

系统不托管私钥、不广播交易、不做法币估值，也不把资金关联解释为地址身份或确定的逐币流向。

## 2. 总体架构

```text
                     +-----------------------+
                     | React 分析控制台      |
                     +-----------+-----------+
                                 |
                     +-----------v-----------+
                     | Echo HTTP API          |
                     | 校验/鉴权/限流/超时   |
                     +-----------+-----------+
                                 |
       +-------------+-----------+-----------+-------------+
       |             |                       |             |
   +---v----+    +---v----+             +----v-----+   +---v----+
   | syncer |    | tracer |             |propagation|   |profile |
   +---+----+    +---+----+             +----+-----+   +---+----+
       |             |                       |             |
       |        +----v-----------------------v-------------v--+
       |        | store: MongoDB Adapter、查询与任务持久化   |
       |        +--------------------+------------------------+
       |                             |
 +-----v------+           +----------v-----------+
 | Etherscan  |           | transactionanalysis  |
 | V2 Adapter |           | bridge / chainrpc    |
 +------------+           +----------+-----------+
                                      |
                             Ethereum / Base RPC
```

`cmd/server/main.go` 是组合根，负责加载配置、连接 MongoDB、构造模块、注册路由并启动后台 Worker。业务代码位于 `internal`，HTTP Handler 不直接操作外部数据源或 Mongo Collection。

## 3. 分层职责

### 3.1 接入层

`internal/httpapi` 使用 Echo 暴露 HTTP 接口，承担：

- 链、地址、方向、深度和资产参数校验；
- Bearer API Key、单进程 IP 限流、Body 上限和请求超时；
- 请求日志、panic 恢复和统一错误结构；
- 同步、Trace 和风险传播的异步任务协议；
- 静态前端资源托管。

主要资源包括：

| 资源 | 用途 |
| --- | --- |
| `/api/v1/sync`、`/api/v1/sync-jobs/:id` | 创建和查询地址同步任务 |
| `/api/v1/edges` | 按方向、资产和游标读取事实边 |
| `/api/v1/trace`、`/api/v1/trace-jobs/:id` | 创建、读取和停止分层资金图任务 |
| `/api/v1/propagation-jobs` | 创建、查询和停止风险关联任务 |
| `/api/v1/transactions/:txHash` | 读取交易与协议解释 |
| `/api/v1/labels` | 写入和查询确定性标签 |
| `/api/v1/bridge-*` | 桥证据分析、状态同步和查询 |

完整请求和响应结构以 [OpenAPI](openapi.yaml) 为准。

### 3.2 应用与领域层

| 模块 | 当前职责 | 关键边界 |
| --- | --- | --- |
| `syncer` | 编排地址历史分页、检查点、缓存、安全链头和批量写入 | 数据来自外部索引器，允许失败和部分结果 |
| `fundgraph` | 查询方向/资产过滤后的原始事实边 | 使用稳定游标，不解释协议或风险 |
| `tracer` | `trace-v1` 资金状态队列、金额预算、时间窗口、终点剪枝和合约资产转换 | 只沿可解释资金事实展开，不代表风险结论 |
| `transactionanalysis` | 解析交易、Receipt、Transfer、WETH 和 Uniswap V3 Swap | 只接受成功且可验证的协议证据 |
| `bridge` | 解析官方 OP Stack Bridge、关联双链消息并推进状态 | 不按金额和时间猜测跨链交易 |
| `profile` | 计算版本化地址活动画像 | `suspected_hot_wallet` 是行为推断，不是身份标签 |
| `propagation` | `propagation-v3` 目标中心风险评估任务 | 只保存关联证据，不复制源标签身份 |
| `risk` | 生成直接标签的风险解释与旧风险结果结构 | 新的多跳关联由 `propagation` 独立负责 |

模块通过窄接口依赖 Store 或外部 Source，测试可以用内存 Stub 替代 MongoDB、Etherscan 和 RPC。

### 3.3 基础设施层

- `internal/etherscan`：Etherscan V2 地址历史和 Proxy RPC Adapter；
- `internal/chainrpc`：Ethereum/Base JSON-RPC 调用和日志过滤；
- `internal/store`：MongoDB 集合、索引、幂等写入、聚合查询和任务租约；
- `internal/chains`：链 ID、名称和链配置注册表；
- Docker：MongoDB、本地服务和前端静态构建。

## 4. 核心数据模型

### 4.1 统一资金事实

三种地址历史被标准化为 `Transfer`：

| 来源 | 链上语义 | 资产 |
| --- | --- | --- |
| `txlist` | 顶层 Transaction 的 value | 原生 ETH |
| `txlistinternal` | 执行轨迹中的 value 转移 | 原生 ETH |
| `tokentx` | ERC-20 `Transfer` Log | Token 合约 |

事实唯一键为：

```text
(chain, txHash, source, traceId, logIndex, asset)
```

同一交易可以包含多条内部转账或 Token Log，因此不能只用 `txHash` 去重。金额以最小单位十进制字符串保存，Go 侧使用 `big.Int`，避免 `float64` 精度丢失。

### 4.2 事实、解释和推断分层

```text
Transfer / transaction / receipt / log / trace
                         |
                         v
       Swap / Wrap / Bridge 等协议解释
                         |
                         v
  Label / Profile / Risk Association 等派生结论
```

上层对象必须保存规则版本、数据水位和证据引用。协议证据不完整时不切换资产或建立跨链边；推断结果不覆盖人工和公开名单标签。

## 5. MongoDB 设计

### 5.1 集合

| 集合 | 内容 | 主要一致性约束 |
| --- | --- | --- |
| `addresses` | 地址同步范围和状态 | `(chain,address)` 唯一 |
| `transfers` | ETH、内部 ETH、ERC-20 事实 | 事实唯一键幂等 upsert |
| `sync_jobs` | 同步状态、检查点和进度 | 任务终态持久化 |
| `trace_jobs` | Trace 参数、依赖和 `trace-v1` 结果 | 查询可通过 Job ID 恢复 |
| `labels` | 人工和公开确定性标签 | `(chain,address,type,source)` 唯一 |
| `address_profiles` | `hot-wallet-v1` 画像快照 | 地址、规则版本和数据水位唯一 |
| `propagation_jobs` | 风险传播参数、租约、重试和结果 | 幂等键唯一，状态和租约可领取 |
| `inferred_risk_associations` | 持久化关联风险 | 源标签、目标、方向、资产、版本和水位唯一 |
| `transaction_analyses` | 交易和协议解释缓存 | `(chain,txHash)` 唯一 |
| `pool_metadata` | 已校验的 Pool 元数据 | `(chain,pool)` 唯一 |
| `cross_chain_links` | 官方桥双链证据和生命周期 | 证据键、协议 identity key 唯一 |

### 5.2 查询索引

`transfers` 分别为 `from` 和 `to` 建立以下索引族：

- 链 + 端点 + 稳定游标字段；
- 链 + 端点 + `assetType` + 稳定游标字段；
- 链 + 端点 + `asset` + 稳定游标字段；
- 链 + 端点 + 资产 + 对手方，用于连续分组聚合。

TopN 查询只投影对手方、金额和必要元数据，MongoDB 按对手方排序。Go 流式累计当前分组，并用固定大小的小根堆保留前 N 个结果。内存由 TopN 或候选上限决定，不随匹配交易数线性增长。

任务集合按状态、创建时间或租约建立领取索引；风险关联按目标地址和 `stale` 状态建立读取索引。

## 6. 核心运行链路

### 6.1 地址同步

```text
创建 sync_job
  -> 读取安全链头与已有检查点
  -> 分别分页读取 txlist / txlistinternal / tokentx
  -> 标准化并批量 upsert transfers
  -> 推进已成功持久化的检查点
  -> 更新 addresses 和任务终态
```

同步使用共享进程内限流、可重试错误分类、Context 取消和区块区间拆分。只有数据写入成功后才推进检查点。

### 6.2 资金链路追踪

```text
创建 trace_job
  -> 确保根地址已同步
  -> 根地址全量查询具体资金事实
  -> 遍历每个 (地址,方向,资产,金额,入口交易) 状态
  -> 按时间方向消费剩余金额并过滤小额
  -> 终点剪枝、环路去重、继续下一层
  -> 遇到未同步节点时创建 sync_job，完成后重试
  -> 持久化 trace-v1 结果
```

根节点查询完整的 ETH 与 Token 事实；普通地址只查询入口区块约束的当前资产。每个状态携带剩余金额，后续分支总量不能超过入口金额。进入支持的合约时只解析锚定交易，只有完整、成功、无歧义的 Swap/Wrap 证据才允许切换资产。跨链桥、未知合约、小额资金和高频地址均作为明确终点。详见[资金链路追踪设计](10-资金链路追踪设计.md)。

### 6.3 风险关联传播

```text
确定性 manual/public-list 标签
  -> 创建 propagation_job
  -> Worker 原子领取并续租
  -> 每个状态合并金额/次数/最近/强制地址候选
  -> 有界 BFS、环路剪枝和确定性终点停止
  -> 保存证据路径和 inferred_risk_associations
```

当前版本为 `propagation-v3`，评分规则为 `risk-association-v2`。查询目标双向最多展开 3 跳，只使用已同步事实；分数是调查优先级，不是违法概率。

同资产优先传播；跨资产只接受已确认 Swap，跨链只接受已确认 Bridge。目标结果表示“与源标签的关联风险”，不修改目标地址的确定性标签。

### 6.4 交易与桥协议解释

交易分析读取 Transaction 和 Receipt，解析 ERC-20 Transfer、WETH Deposit/Withdrawal 和 Uniswap V3 Swap，并通过 Pool 的 `factory()`、`token0()`、`token1()` 等只读调用验证协议身份。

桥分析只支持已注册的 Ethereum/Base 官方 OP Stack 合约。系统使用消息哈希或协议证据关联源链与目标链事实，并维护 `initiated`、`proven`、`finalized`、`completed`、`failed`、`ambiguous` 等状态。

## 7. 任务与并发模型

同步和 Trace 使用进程内有界队列执行，任务状态保存在 MongoDB；服务可以展示失败、停止和部分结果，但它们还不是完整的多实例分布式调度器。

风险传播采用更完整的持久化任务模型：

- 使用源标签版本、查询参数、传播版本和数据水位生成幂等键；
- MongoDB 原子领取 `queued` 或租约过期任务；
- Worker 定期续租，最多重试 3 次；
- Context 取消会停止本地执行并持久化终态；
- 新任务完成后，不同传播版本或数据水位的旧关联标记为过期。

所有层级都向上传递错误。游标解码、非法金额、RPC 失败和 Context 取消不会被静默转换为空结果。

## 8. 版本与结果语义

| 能力 | 当前版本 | 语义 |
| --- | --- | --- |
| 资金链路 | `trace-v1` | 逐笔资金事实、FIFO 归因、金额预算和证据化资产转换 |
| 地址画像 | `hot-wallet-v1` | 基于活动特征的行为推断 |
| 风险传播 | `propagation-v3` | 目标中心双向有界评估 |
| 传播评分 | `risk-association-v2` | 距离、时间、金额和协议因子，多源饱和聚合 |

前端只展示当前 Trace 和传播版本。旧任务保留用于审计，不混入当前结果。

## 9. 部署边界

Demo 使用一个 Go 进程、MongoDB 和静态 React 页面即可运行。RPC 是交易和协议证据来源，Etherscan 是地址历史索引来源；二者不能互相完全替代。

生产级部署需要补齐分布式任务、集中配额、链重组恢复、持续索引、可观测性和容量治理，详见 [Demo 边界与生产化](03-Demo边界与生产化.md)。
