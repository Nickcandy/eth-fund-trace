# 追踪加速与下一阶段

## 1. 目标

把“交互式调查”与“全历史归档”解耦，使一次 Demo 查询具有可预测的时延、API 调用量和 Mongo 增量，同时保持数据完整度可解释。

本文是推荐实施方案，尚未全部落地。

## 2. 三种工作模式

| 模式 | 目的 | 默认数据范围 | 超限行为 |
| --- | --- | --- | --- |
| `bounded_address` | 快速查看一个地址的主要邻居 | 最近优先、有界样本 | `partial/truncated`，高频节点停止展开 |
| `anchored_transaction` | 从某笔交易追踪资金前后关系 | 以 txHash 区块为时间锚点 | 保持路径区块单调，预算内展开 |
| `archive_address` | 完整归档和画像 | 全历史 | 后台长任务，可消耗大量配额 |

控制台默认使用 `bounded_address`；完整归档必须由用户显式触发。

## 3. 地址追踪如何加速

### 3.1 预算模型

建议初始默认值：

```text
单地址最大 API 页数       100
单地址最大有效事实边      10,000
单地址最长同步时间        2 分钟
单任务最大同步地址        50
单任务最大 API 页数       500
单任务最大 Mongo 新事实边 100,000
```

阈值需要用真实 Demo 地址压测后调整，不能作为 Etherscan 官方限制解释。

### 3.2 最近优先

交互式模式使用倒序分页，先获得最近活动。每个方向和资产组取得足够的 Top-N 候选后即可停止。归档模式仍可升序同步并推进连续游标。

### 3.3 数据状态

为地址和任务增加：

```text
coverageMode: full | bounded | anchored
dataStatus: complete | partial | truncated
truncationReason: page_budget | record_budget | time_budget | task_budget
observedPages, observedRecords
rangeStart, rangeEnd
sampleOrder: asc | desc
```

只有 `complete` 可以推进“全历史已覆盖”游标。`bounded` 样本不能冒充完整同步缓存。

### 3.4 高频节点剪枝

达到预算时：

1. 提交已确认事实边；
2. 标记 `structuralClass=high_volume_hub`；
3. 标记当前结果为截断样本；
4. 保留进入该节点的路径；
5. 将其作为本次 TraceJob 的终点，不继续 BFS；
6. 可基于样本生成画像，但必须显示 `sampled=true`；
7. 不自动生成确定性 `hot_wallet` 标签。

## 4. 如何判断热钱包

### 4.1 先判断账户类型

在指定数据区块调用 `eth_getCode`：空代码通常表示 EOA，非空表示合约。结果保存判断区块，不能假定永久不变。

### 4.2 `hot-wallet-v2` 推荐输入

- 账户类型及判断区块；
- 最近 30 天或最多 10,000 条有界样本；
- 入账、出账和双向最低事件数；
- 独立发送方、接收方和总对手方；
- 活跃天数与时间分布；
- 多方汇入后转出、收到后批量分发模式；
- 样本覆盖区块、截断状态和数据源。

### 4.3 输出层级

```text
insufficient_data
low_signal
high_activity_candidate
suspected_hot_wallet
```

另行输出结构分类：

```text
normal | high_volume_hub | contract_infrastructure
```

只有人工或可信公开证据才能写入 `exchange_hot_wallet` 等确定性标签。

## 5. 如何追踪某一笔交易

### 5.1 请求模型

```http
GET /api/v1/trace-transaction
  ?chain=ethereum
  &txHash=0x...
  &direction=both
  &depth=3
  &topN=10
  &blockWindow=100000
```

### 5.2 锚点解析

通过 RPC 获取交易和 receipt：

- 顶层 ETH：交易 `from/to/value`；
- ERC-20：解析 receipt 中的 `Transfer` logs；
- 内部 ETH：查询支持历史 trace 的数据源；
- 一个交易可能产生多条不同资产事实边，用户需要选择锚点边或按资产分别追踪。

### 5.3 时间有向路径

如果锚点在区块 `B`：

- 上游只允许 `blockNumber <= B`，沿路径区块单调不增；
- 下游只允许 `blockNumber >= B`，沿路径区块单调不减；
- 每一跳以当前路径边的区块作为下一跳时间边界，而不是一直使用最初的 `B`。

这比简单设置 `startBlock=B` 更严格。只设置 startBlock 会完全丢掉上游来源，并把地址其他无关交易混进路径。

### 5.4 归因限制

交易锚点只能证明事实上的先后和地址交互，不能证明后续转账使用的是同一笔资金。账户余额是可替代的；没有 UTXO 式的一一对应关系。结果应称为“时间一致的资金关联路径”，而不是确定的逐币流向。

## 6. Module 调整

### 6.1 `syncer`

建议收敛为一个深接口：

```go
Sync(ctx context.Context, request SyncRequest) (SyncJob, error)
```

`SyncRequest` 包含 mode、预算、区块窗口和排序。分页、进度、截断和完整度全部隐藏在 module 内。

### 6.2 `tracer`

追踪查询增加 mode 和可选锚点：

```go
type Query struct {
    SeedAddress string
    Anchor      *TransactionAnchor
    Budget      TraceBudget
    // direction, depth, topN, asset...
}
```

Graph module 只消费满足覆盖要求的事实边；同步策略由编排器决定，避免图算法直接假定“地址必须全历史完整”。

### 6.3 `profile`

画像输入增加 `DataCoverage`，快照唯一键需要包含覆盖模式或样本版本。完整数据画像与截断样本画像不能命中同一缓存键。

### 6.4 `store`

增加字段级进度更新，避免每个 Etherscan 页面 `ReplaceOne` 整份任务。建议 500ms-1s 节流 `$set/$inc`，终态同步持久化。

## 7. 实施阶段

### P0：控制当前风险

- 为交互式同步增加页面、记录和耗时预算；
- 增加 `partial/truncated` 和 `high_volume_hub`；
- 超限节点停止 BFS；
- 前端展示覆盖范围和截断原因。

验收：高频地址在预算内结束，TraceJob 不再无限 `waiting_sync`。

### P1：快速地址追踪

- 最近优先采样；
- 分方向/资产收集 Top-N；
- 任务级共享预算；
- 进度写入节流。

验收：固定高频地址的 API 页数和时延不超过配置预算。

### P2：交易锚点与 DEX 语义

- P2.1：新增交易/Receipt Adapter，解析顶层 ETH、ERC-20 和 WETH 事实；
- P2.2：验证 Uniswap V3 Pool，解析 Universal Router 下的逐段 Swap；
- P2.3：从明确输出地址衔接现有地址追踪，并显式标注其不是逐币归因；
- P2.4：后续增加路径区块单调约束，再扩展 Uniswap V2 和 1inch。

验收：固定 txHash 的发起人、Router、Pool、逐段输入输出和证据质量正确；未知协议不被误认为 Uniswap。

### P3：画像升级

- 增加 EOA/合约判断；
- 实现 `hot-wallet-v2` 与样本完整度；
- 将结构分类与业务标签拆开；
- 使用固定样本图校准阈值并版本化。

验收：高频合约不会被误判为 EOA 热钱包；截断画像不会显示为完整结论。

### P4：M12 官方桥识别与状态同步

- 识别 Ethereum↔Base 官方 OP Stack Bridge 的 ETH/ERC-20 存款和提款；
- 复用 `cross_chain_links`，通过消息哈希/nonce 和双端事件证据幂等配对；
- 对提款支持 `initiated/proven/finalized/completed` 生命周期和有界后台轮询；
- 未知合约、证据冲突和上游暂不可用分别降级，不修改地址追踪模型。

验收：固定桥接样本能够自动生成一条可审计跨链图边，目标事实出现后状态可推进到 `completed`，重复扫描不产生重复边。

## 8. 关键测试

- 预算边界恰好命中、超过一页和 Context 取消；
- 截断不推进完整游标；
- 同一事实边边界重读仍幂等；
- 单区块超过上游页限时明确失败；
- 高频节点保留到达边但停止扩展；
- 上游区块单调不增、下游单调不减；
- EOA、合约、截断样本的画像分类；
- 服务重启后的任务终态和前端 URL 恢复。
